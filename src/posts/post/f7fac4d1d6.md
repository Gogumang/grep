그런데 만들고 나서 가장 오래 붙잡고 있었던 건 검색이 아니었습니다. 만든 것이 제대로 동작하는지 확인하는 일이었습니다.

이번 편은 그 이야기입니다. 질의를 던졌을 때 무엇이 오갔는지 보이게 만들고, 그게 맞는 답인지 채점하고, 그렇게 검증한 검색을 에이전트가 쓸 수 있게 내보내기까지. 그리고 마지막에는 그렇게 만든 도구가 지금 어디에서 어떻게 쓰이고 있는지까지의 이야기입니다.

### LLM Observability와 LLM 평가하기

LLM과 RAG는 잘 돌아가고 있는지 눈으로 확인하기 어려운 시스템입니다. LLM의 입출력은 자연어이다 보니, 지금 모델이 좋은 답변을 했는지 못했는지를 판단하기가 굉장히 어렵습니다.

답이 그럴듯하면 맞아 보입니다. 근거 문서들을 함께 돌려주니 더 그래 보입니다. 실제로는 엉뚱한 문서를 집어왔는데도 모델이 매끄럽게 문장을 만들어내면, 읽는 사람은 그걸 알아차리기가 어렵습니다. 비용도 마찬가지입니다. 문서 하나를 처리하는 데 LLM 호출이 몇 번이나 붙는지, 그게 한 달에 얼마가 되는지는 청구서가 오기 전까지 알 수 없습니다.

이런 문제점을 해결해주는 도구로써 최근에 LLM에 특화된 APM(Application Performance Monitoring)들이 나왔습니다. 그 중 저희는 **Langfuse**를 선택했습니다. LLM 애플리케이션에 특화된 오픈소스 관측 플랫폼으로, 요청 하나가 어떤 경로를 거쳤는지를 trace 단위로 기록하고 보여주는 모니터링 툴입니다.

![](https://images.gogumang.com/f7fac4d1d6/01.png)

*Langfuse trace 추적 예시*

일반적인 APM과 다른 점은, 프롬프트와 응답 전문, 사용 토큰, 모델별 단가에 따른 비용이 호출마다 남는다는 점입니다. 검색 → 프롬프트 조립 → 생성으로 이어지는 여러 단계를 하나의 trace로 묶어 보여주기 때문에, 어느 단계에서 시간이 걸렸고 어디서 토큰이 나갔는지를 한 화면에서 확인할 수 있습니다.

#### RAG 평가 파이프라인 구축

Langfuse를 붙이면서 어디에 시간과 비용이 나가는지 보이게 됐습니다. 다만 검색 결과가 좋은지 나쁜지는 여전히 알 수 없었습니다. *trace에 남는 건 무엇이 오갔는지, 그게 맞는 답인지가 아니기 때문입니다.*

Langfuse에는 **Experiment**라는 이름으로 해당 기능을 지원하고 있습니다. 데이터셋을 만들고, 평가체계를 구축하고, 실험을 돌려 결과를 남기는 것까지 하나의 플랫폼 안에서 가능합니다. 이번 프로젝트에서는 이 기능을 최대한 활용하였습니다.

#### 무엇을 물어볼 것인가

RAG 시스템을 평가하기 위해선, 먼저 평가대상인 질문-답변 쌍을 제작해야했습니다.

검색이 실패하는 방식은 하나가 아니기 때문에 먼저 사내 지식을 기반으로 답변할 수 있는 질문 유형을 일곱 가지로 나누고, 유형별로 질문과 정답 쌍을 작성했습니다. 유형을 나눠서 데이터셋을 생성한다면, 평가 이후 어디가 약한지가 점수와 함께 드러날 것이라고 생각했습니다.

![](https://images.gogumang.com/f7fac4d1d6/02.png)

#### 검색이 제대로 됐는가

질문셋이 준비됐으니 이제 확인할 차례입니다. RAG에서 답이 틀리는 경로는 크게 둘인데,

* 애초에 엉뚱한 문서를 가져왔거나
* 문서는 맞는데 모델이 잘못 읽은 경우입니다

앞쪽은 정보 검색 분야에서 오래 쓰인 지표들로 확인할 수 있습니다.

* **Recall@5** : 정답 문서가 상위 5개 안에 들어왔는가
* **Hit Rate** : 정답 문서를 한 번이라도 회수했는가
* **MRR** : 정답 문서가 몇 번째로 올라왔는가

질문마다 정답 문서를 지정해뒀기 때문에 리트리버가 돌려준 목록과 대조하면 자동으로 계산됩니다. Langfuse Python SDK로 데이터셋을 불러와 실험을 돌리고, 이 지표들을 계산하는 evaluator를 붙였습니다. LLM을 거치지 않으니 빠르고, 같은 입력에는 항상 같은 값이 나옵니다.

#### 그래서 답은 좋아졌는가 (LLM-as-a-judge)

다만 이 지표들이 좋아진다고 최종 답변이 좋아진다는 보장은 없습니다. 정답 문서를 1등으로 가져와도 모델이 엉뚱한 문단을 인용할 수 있고, 반대로 순위가 낮아도 Agent가 검색을 몇 번 더 해서 결국 답을 찾아낼 수도 있습니다. 저희가 최종적으로 만드는 건 Agent가 쓰는 도구이니, **최종적으로 확인해야 할 건 그 도구를 쓴 Agent의 답변입니다.**

![](https://images.gogumang.com/f7fac4d1d6/03.png)

*LLM as a judge 동작 과정*

그래서 MCP를 붙인 Agent를 하나 만들어 답변까지 생성하게 했습니다. 남은 문제는 채점입니다. 답변이 자연어라 맞았는지 틀렸는지를 문자열 비교로 가를 수 없고, 그렇다고 실험할 때마다 사람이 수십 건을 읽어 점수를 매길 수도 없습니다. 채점은 답변을 만든 모델과 분리된 LLM에게 맡겼습니다. 이를 **LLM-as-a-judge** 라고 합니다. 미리 작성해둔 정답과 실제 응답을 함께 넘겨 0에서 1 사이의 *“* 정확도*”* 점수를 매기게 했습니다. 정답을 함께 주는 게 중요합니다. 심판이 혼자 판단하는 게 아니라 정답표를 들고 채점하는 셈이라, 점수가 덜 흔들립니다.

평가 파이프라인을 정리하면 두 층으로 측정을 합니다. 검색 지표는 리트리버가 옳은 문서를 가져왔는지를 보고, LLM-as-a-Judge는 그 문서로 만든 답이 실제로 답변이 되는지를 확인합니다. 답이 틀렸을 때 검색이 문제였는지 생성이 문제였는지, 두 층을 비교하면 가려집니다.

프로젝트의 모든 변경은 이 평가 파이프라인을 통과합니다. 프롬프트에서 문장 하나를 지우든 툴의 파라미터를 바꾸든, 먼저 실험을 돌려 점수를 보고 수정 사항을 적용할지를 정했습니다. 실험은 한 번으로 끝내지 않고 보통 3회 이상 반복해 평균을 냈습니다. LLM 응답에는 편차가 있어서, 한 번의 결과로는 개선인지 운인지 구분할 수 없기 때문입니다. Run마다 정확도와 함께 지연시간·토큰·비용이 같이 남기 때문에, “정확도는 그대로인데 토큰만 줄었다”처럼 한 축만 움직인 변경도 그대로 보였습니다.

### MCP 서빙

남은 건 지금까지 준비한걸 어떻게 Agent에게 제공하느냐입니다.

MCP 서빙 도구로는 **FastMCP**를 택했습니다. Python으로 MCP 서버를 만들 때 사실상 표준처럼 쓰이고 있고, 데코레이터 하나로 함수 시그니처와 타입 힌트에서 툴 스키마를 자동으로 만들어줍니다. 저희처럼 툴 명세(docstring과 파라미터 설명)를 자주 고치는 상황에서는, 명세가 코드 옆에 붙어 있어 함께 관리된다는 점이 특히 편했습니다.

transport 방식은 HTTP Streamable을 골랐습니다. LLM 호출 권한과 LightRAG 접근 권한이 서버에만 있어야 했기 때문입니다. stdio 방식이라면 사용자 로컬에서 서버가 뜨면서 이 권한들이 함께 나가야 하는데, 그럴 수는 없었습니다. 서버를 한 곳에 두고 사내 에이전트들이 원격으로 붙는 구조가 맞았습니다.

단순하게 생각하면 MCP 서버를 띄우고 필요한 도구를 연결해주는 것으로 서빙은 끝이라고 생각할 수 있지만, 생각보다 고려할 점이 많았습니다. MCP는 툴 정의와 명세만 주어지기 때문에, 그걸 어떻게 사용할지는 온전히 에이전트의 자유입니다. 의도한 동작 흐름이 있어도 에이전트가 이를 무시하면 기대보다 못한 결과가 나올 수 있습니다.

저희 MCP는 크게 세 가지 동작을 제공합니다.

1. 의미 기반으로 chunk 가져오기 (get_lightrag_kg)
2. 특정 요소의 주변 관계망 탐색하기 (get_page_hierarchy / get_issue_hierarchy)
3. 특정 요소의 실제 내용 읽기 (read_confluence_page / read_jira_issue)

저희가 의도한 건 1 → 2 → 3을 유기적으로 오가며 답변에 필요한 근거를 에이전틱하게 모으는 흐름이었습니다. 그런데 처음에는 1을 한 번 호출하고 바로 답을 만들어버렸습니다. 청크 몇 개로 그럴듯하게 답변을 하지만, 2편에서 이야기한 “문서가 어디에 놓여 있는가”는 전혀 쓰이지 않는 상태였고 기대보다 아쉬운 답변을 생성했습니다.

![](https://images.gogumang.com/f7fac4d1d6/04.png)

*MCP Protocol의 Initialization Phase에서 Instructions이 전달*

결국 MCP에 붙는 에이전트들에게 툴 오케스트레이션을 의도적으로 알려줄 필요가 있었고, 이를 **서버 instructions**로 해결했습니다. MCP 서버는 클라이언트와 연결하는 초기화 절차에서 instructions를 함께 내려보낼 수 있고, 클라이언트는 해당 텍스트를 LLM 컨텍스트에 실어줍니다. 즉 툴 목록과 함께 “이 툴들을 이런 순서로 쓰라”는 안내가 같이 전달되는 셈입니다. 지시를 충실히 따르는 모델이라면 의도한 대로 움직이게 됩니다.

```
### 예시: "공통 카프카 토픽 명명 규칙이 어떻게 되나요?"

1. get_lightrag_kg(query="공통 카프카 토픽 명명 규칙")
   → chunks 중 path = "공통플랫폼개발팀/.../공통카프카/공통카프카 요청 가이드" 확보

2. KG가 알려준 path 하나에 만족하지 말고, 부모 경로의 hierarchy도 함께 확인
   - get_page_hierarchy(path="공통플랫폼개발팀/.../공통카프카")
     → 같은 레벨의 형제 문서(예: "공통카프카 주의사항") 발견

3. 발견된 관련 페이지를 모아 읽기
   - read_confluence_page(path="...공통카프카 요청 가이드")

4. 명명 규칙과 그 예외·제약이 출처와 함께 모두 확보되면 종료, 답변 작성
```

물론 다른 방법도 있습니다. MCP를 사용하는 Skill을 따로 만들어 제공할 수도 있었겠지만, MCP 쪽에서 Skill 사용을 강제할 수는 없으니 같은 문제가 반복될 수 있습니다. 그래서 instructions에 담는 방향으로 확정했습니다.

### 측정하고, 고치고, 다시 측정하기

*서빙을 붙이고 나서 손댄 것은 리트리버가 아니라 MCP 명세였습니다.* 서버 instructions와 툴 docstring, 파라미터의 형태가 에이전트가 우리 도구에 대해 아는 전부이고, 여기에 성능이 생각보다 민감하게 반응했습니다. 그래서 명세를 대상으로 프롬프트 엔지니어링을 진행했습니다.

#### 프롬프트는 짧을수록 좋았다

*가장 크게 효과를 본 건 프롬프트를 줄이는 작업이었습니다.* 경량 모델을 사용할수록 긴 프롬프트의 중간부 지시를 흘리는 *경향(lost in the middle*)이 강해서, 규칙을 촘촘히 적어둘수록 오히려 덜 지켰습니다.

MCP instructions와 툴 docstring에서 중복된 지시들을 걷어내고 핵심만 남겼습니다.

#### 도구 명세도 프롬프트입니다

trace를 열어보면 도구를 만든 방식 때문에 틀리는 경우가 적지 않았습니다. 도구의 이름과 설명, 파라미터 형태는 모델이 읽는 또 하나의 프롬프트입니다. 두 가지를 고쳤습니다.

1. **한 번에 여러 개를 받던 것을 하나씩 받도록**. 문서를 읽는 도구는 원래 페이지 목록을 한꺼번에 받았습니다. 호출을 아끼는 효율적인 설계처럼 보였지만, 결과가 목록으로 돌아오면 모델은 어느 결과가 어느 요청에 대한 것인지부터 맞춰봐야 합니다. 문서를 읽기도 전에 짝을 맞추는 데 생각을 쓰는 셈입니다. 여러 개가 필요하면 도구를 여러 번 부르면 그만이라, 한 번에 하나씩만 읽도록 바꿨습니다.
2. **사람이 읽기 좋은 값 대신 기계가 다루기 좋은 값으로**. 문서를 식별할 때 처음에는 팀/폴더/제목 같은 경로를 사용했습니다. 그런데 제목 자체에 슬래시가 들어가 있는 경우 폴더 구분과 헷갈리지 않도록 따로 특수기호로 표시해두는데, 모델이 그 표시를 오타로 보고 지워버리는 일이 생겼습니다. 한 글자 차이로 문서를 못 찾으니 빈 결과가 돌아옵니다. 이후 모델이 다듬을 여지가 없는 고유 ID로 바꿨습니다.

둘 다 검색을 건드린 수정이 아닙니다. 무엇을 어떤 모양으로 건네줄지를 바꿨을 뿐인데 정확도가 모델에 따라 3\~9%p 움직였습니다. 에이전트는 우리가 준 명세만 보고 판단하니, **명세를 다듬는 일이 곧 성능을 다듬는 일이었습니다.** 그리고 그 효과는 경량 모델일수록 크게 나타났습니다.

1편에서 미리 보여드린 숫자는 범용 문서 검색 MCP와 저희가 구축한 Atlas Retriever MCP를 비교한 결과입니다.

![](https://images.gogumang.com/f7fac4d1d6/05.png)

주목할 만한 건 정확도와 토큰이 함께 좋아졌다는 점입니다. 보통은 근거를 더 넣어 정확도를 사고 토큰을 지불하는데, 여기서는 필요한 문서를 곧바로 찾으니 헤매는 왕복이 줄었고 모델에게 넘기는 것도 문서 전체가 아니라 근거가 될 부분만으로 충분했습니다.

다만 저희가 만든 평가셋으로, 사내 문서를 대상으로 잰 값입니다. 문서를 모으고, 검색을 얹고, 명세를 다듬어 여기까지 온 결과입니다.

### 지금은 어디에 쓰이고 있나

1편에서 챗봇 대신 MCP를 만들기로 했다고 썼습니다. 질문을 받는 창구가 슬랙봇이든 사내 에이전트든 각자 쓰는 코딩 도구든 상관없고, 저희는 사내 지식에서 근거를 찾아 돌려주는 일만 맡겠다는 이야기였습니다.

![](https://images.gogumang.com/f7fac4d1d6/06.png)

*프로젝트의 추상화된 전체 아키텍처*

지금은 세 곳에 붙어 있습니다.

**기술지원봇**은 Slack으로 들어온 기술 문의에 답변 초안을 달아주는 봇입니다. 문의가 등록되면 봇이 관련 문서를 찾아 초안을 만들고, 담당자가 확인한 뒤 문의자에게 전달합니다. 저희 MCP는 이 봇이 사내 문서를 찾을 때 쓰는 도구입니다.

**YAPP**은 사내 AI 에이전트 플랫폼입니다. 사내 도구들을 MCP로 연결해 두고, 사용자가 쓸 도구를 골라 웹이나 Slack에서 대화하듯 일을 맡기면 결과를 돌려받는 구조입니다. Atlas Retriever MCP도 그 목록에 올라가 있어, 사내 문서를 찾아야 할 때 골라 쓰면 됩니다.

**개인 개발 환경**에도 붙여 씁니다. 사내 공용 서버가 떠 있으니 다른 MCP를 연결할 때처럼 클라이언트 설정에 주소만 추가하면 됩니다.

처음에는 저희 팀 문서만 넣고 시작했습니다. 지금은 전사 Confluence와 Jira가 대상이고, 지원봇도 팀 하나가 아니라 실 단위로 쓰이고 있습니다. 문서는 하루 세 번 증분으로 따라붙기 때문에, 어제 새로 쓴 가이드도 오늘 답변의 근거가 됩니다.

### 마치며

여기까지가 만든 것을 확인하고 내보내기까지의 이야기입니다.

Langfuse로 무엇이 오갔는지 보이게 만들었고, 질문 유형을 일곱 가지로 나눠 평가셋을 만든 뒤 검색 지표와 LLM-as-a-judge 두 층으로 채점했습니다. FastMCP로 서빙하면서는 툴을 어떤 순서로 쓸지를 서버 instructions에 담았고, 끝으로 명세를 줄이고 다듬는 일로 정확도를 끌어올렸습니다.

물론 끝난 건 아닙니다. 임베딩 모델은 계속 세대가 바뀌고, 바뀔 때마다 전 문서를 다시 임베딩해야 합니다. 평가셋도 유형별로 더 촘촘히 채워야 하고, 사내 문서가 늘어날수록 무관한 문서가 섞여 들어오는 문제도 계속 손봐야 합니다. 다만 고칠 때마다 나아졌는지는 잴 수 있게 됐습니다.

이 시리즈를 이런 이야기로 시작했습니다. 같은 질문이 슬랙 DM으로 계속 돌아오고, 답을 아는 사람이 자리를 비우면 응답이 그대로 밀린다는 이야기였습니다. 지금은 그 자리에 초안이 먼저 놓입니다.
