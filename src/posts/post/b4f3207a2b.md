안녕하세요. 카카오톡 숏폼 추천 모델을 개발하고 있는 루퍼트(rupert)입니다.

저희 추천팀은 추천 지표 분석에 AI 에이전트를 사용합니다.

AI 에이전트에게 분석을 요청하면, 에이전트가 미리 정리해 둔 지침 문서(`CLAUDE.md`)를 읽고 SQL을 작성해 기존 Hadoop 환경에서 실행한 뒤 집계 결과를 리포트로 완성합니다. 지난 글에서는 데이터 엔지니어, 분석가만 알고 있던 로그 데이터 접근 방법과 분석 기준을 AI를 통해 조회하는 사례를 소개했습니다.

이번 글은 그 환경을 팀에서 함께 사용하면서 마주한 문제와, 이를 해결한 방식에 관한 이야기입니다.

## 1. 기존 분석 자동화 환경의 한계

추천팀의 개발자 A와 B가 동일한 추천 지표를 각자의 AI에이전트로 분석했습니다. 그런데 같은 ‘재생수’ 값이 분석한 사람에 따라 다르게 뽑히는 일이 생겼습니다.

원인을 살펴보니 개발자A는 영상 플레이어의 수집 로그를, 개발자B는 앱의 수집 로그를 사용하고 있었습니다. 두 수집기는 영상 소비를 서로 다른 기준으로 기록합니다. 그래서 분석 목적에 따라 골라 써야 하는 로그였습니다. 어느 한쪽이 틀린 데이터는 아니었지만, 쿼리가 실행되고 결과가 나왔다는 사실만으로는 두 숫자를 같은 의미로 비교할 수 없었습니다.

정리하면 기존 구조의 한계는 3가지였습니다.

**1. 데이터의 암묵지**: 지표 분석시, 어떤 로그를 선택하고 어떤 기준을 적용해야 하는지는 분석을 맡은 사람이 경험으로 보완하던 부분이었습니다. AI에이전트가 분석을 수행하려면 명시적으로 해소해야 하는 '데이터의 암묵지’에 대한 팀 공통의 기준은 없었습니다.

**2. 분석의 방법**: 과제에 따라 어떻게 분석 결과를 도출할지, 무엇과 비교할지가 달랐습니다. 사용하는 LLM 모델에 따라 리포트의 내용과 구성, 문체에도 차이가 생겼습니다.

**3. 분석의 배경**: 분석은 과제의 질문에 답하기 위한 것입니다. 왜 이 분석을 하는지, 어떤 가설을 세웠는지에 따라 봐야할 지표가 달라집니다. 그런데 과제의 맥락은 사람의 머릿속에만 있었습니다.

결국 분석 리포트 수치를 맞춰보고 분석이 적절한지 다시 확인해야 했습니다. 개인별 지침 문서에 지식을 쌓는 방식에서, **팀이 함께 관리하는 지식베이스와 과제의 맥락**으로 바꿀 필요가 있었습니다.

## 2. 팀 분석 자동화에 필요한 3가지 컨텍스트

### 2.1. 컨텍스트별 역할

에이전트가 분석 전에 읽는 정보, 즉 컨텍스트를 다음 세 가지 질문으로 나눴습니다.

|           구분           |  역할  |                                         답해야 할 질문                                         |
|------------------------|------|------------------------------------------------------------------------------------------|
| 1. **Data Catalog**    | What | **데이터 암묵지 해소** - 무엇을 어떤 기준으로 집계하는가? - 데이터의 의미, 로그 선택 기준, 집계 규칙, 주의사항                     |
| 2. **Analyst Persona** | How  | **분석 방법 가이드** - 어떻게 비교·검증하고 결과를 전달하는가? - 분석 절차, 해석 원칙, 리포트 구성과 문체                        |
| 3. **Task Context**    | Why  | **분석의 배경 브리핑** - 왜 분석하며, 어디까지 확인했고, 다음에는 무엇을 판단해야 하는가? - 과제의 목적과 가설, 진행 경과, 검증 결과와 후속 질문 |

이렇게 나눈 이유는 **정보를 재사용하는 범위와 갱신하는 이유가 다르기 때문**입니다. 지표 정의는 여러 분석에서 함께 사용하고, 비교·검증 방법도 과제에 맞게 반복해서 적용합니다. 반면 특정 실험에서 무엇을 확인했고 다음에 무엇을 판단할지는 그 과제가 진행되면서 바뀝니다.

### 2.2. 컨텍스트별 배치와 도구 연결

**AI Data Workspace** (분석 업무 작업공간)

* Data Catalog와 Analyst Persona 관리
* 분석에 사용한 SQL과 결과, 근거와 리포트 보관
* Task Context는 Jira에 저장되며, 에이전트는 Jira 연결 도구(Skill)로 과제 배경지식을 브리핑 받음

```text
AI Data Workspace
├── CLAUDE.md                           # 진입점. 읽을 순서와 금지 사항만 적는다
├── data_sources/
│   └── //_/      # 분석 산출물. README · queries/ · results/ · report.html

(Jira 이슈 · 댓글)                      # [Why] Task Context. 저장소 밖에서 연결 도구로 읽는다

아래는 세 컨텍스트와 AI 에이전트, 데이터 실행과 기록의 관계를 팀의 도구에 대응시킨 그림입니다.

3. 세 가지 컨텍스트의 구성
2장에서 나눈 세 컨텍스트를 각각 어떻게 만들고 관리했는지 살펴봅니다.

3.1. Data Catalog: 데이터 암묵지 해소
Data Catalog는 로그 테이블의 스키마 밖에 있던 팀의 사용 기준을 문서로 옮긴 것입니다. Google Cloud가 데이터와 시스템 주변의 지식을 Markdown 문서로 표현하는 Open Knowledge Format(OKF) 가이드를 제시한 사례가 있는데, 저희는 이 컨셉에 착안해 추천 분석의 목적에 맞는 팀의 Data Catalog를 만들었습니다.

단위: 테이블 하나에 문서 하나 (data_sources//.md구조: 테이블의 성격 → 메타 정보 → 주의할 컬럼 → 집계 규칙 → 데이터에서 확인한 사실내용: 전체 스키마가 아니라 그 테이블을 쓸 때 헷갈리기 쉬운 점과 집계 규칙. 실제 컬럼과 타입은 분석 시작 시 다시 조회작성 원칙: 스키마·파티션·값의 분포 같은 사실은 LLM 분석결과로 채우고, 유효재생 기준처럼 정책에 해당하는 정의는 사람이 작성함예를 들어 플레이어 로그와 앱 로그 중 어느 것을 사용할지, cold 사용자를 ‘최근 N일 동안 유효재생이 없는 사용자’로 정하는 것은 스키마에는 없는 팀의 논리적 정의입니다. 원천 데이터의 구조는 그대로 두고 그 위에 조직이 합의한 지표와 해석 규칙을 얹는다는 점에서, 팀 카탈로그는 semantic layer에 가깝습니다.Data Catalog 예시# play_log

사용자-콘텐츠 시청 로그. 주간 지표·A/B 테스트·전후 비교의 기본 데이터 소스.
집계·파생 지표·필터 규칙의 정의는 이 문서가 기준.

- 테이블 타입: EXTERNAL (Parquet)
- 파티션: date_id(YYYY-MM-DD) + hour_id(HH). 복합 파티션 → 반드시 필터
- 보유 기간: 2025-11 ~ (2026-07-16 실측)

## 컬럼 정보
| 컬럼 | 타입 | 주의사항 |
|---|---|---|
| user_id | string | 원본 식별자. 보고용 산출물에 노출 금지 |
| watch_length | double | 시청 시간, 단위 = 초. `>= y` 로 y초 재생 판정 |
| watch_percentage | double | 1.0 초과 가능 → cap 필수 |
| valid_view | boolean | 유효재생(x초 이상). 서비스 공식 기준 필드 |
| valid_view_flag | boolean | 스키마엔 있으나 미사용 → 아래 절 |
| action_name | string | 분석은 `play_end` 만 |
| reco_type | string | `reco` 가 추천 성능 집계의 기본 모수. 그 외 값은 제외 |
| experiment_key | string | 미배정 = `''` 또는 NULL. `= ''` 필터면 자연 제외 |

## 집계 규칙
| 지표 | 수식 |
|---|---|
| VVR(유효재생률) | valid_views / total_views |
| y초 재생률 | SUM(watch_length >= y) / total_views |
| 인당 재생수 | total_views / COUNT(DISTINCT user_id) |

## 데이터에서 확인한 사실
- valid_view_flag 는 전 행 false (2026-06-10 확인, 근거: <분석 폴더>/results/…) → 유효재생 판정은 valid_view 를 쓴다
1장의 재생수 문제는 이 문서의 첫 줄에서 풀립니다. 재생 로그 카탈로그가 ‘주간 지표·A/B 테스트·전후 비교의 기본 데이터 소스’라고 못 박고, CLAUDE.md가 분석을 시작할 때 카탈로그부터 읽게 하므로, 개발자 A와 B가 같은 요청을 하면 에이전트는 같은 로그에서 출발합니다. 다른 목적에 쓰는 로그는 그 테이블 문서의 첫 줄에 용도가 적혀 있어, 어느 로그를 고를지가 문서에 남습니다.3.2. Analyst Persona: 분석 패턴의 통일분석 패턴은 Analyst Persona라는 지침으로 통일했습니다. 과거 분석 사례들에서 분석 원칙을 추출하여 만든 페르소나(analyst-persona.md)입니다.
페르소나 목표: 누가 분석하든 같은 수준의 검증 절차에서 출발하게 하는 것
절차 6단계: 분석 유형 분류 → 분석 설계 → 함정 점검 → 분석 → 해석 → 리포트 작성
함정 점검: 이상 신호를 행동 변화로 단정하기 전에 로그 수집이나 서비스 변경의 영향부터 확인
리포트 구성: 핵심 결론을 먼저 쓰고 비교 조건·근거·SQL을 이어 붙이며, 확인된 사실과 추정을 구분
분석 패턴을 사용하되, 과거 분석 히스토리를 참고하지 않습니다. 과제마다 목표와 성공 지표가 다르기 때문입니다. 예를 들어 한 과제는 시청시간을, 다른 과제는 소비한 영상 수를 주요 지표로 둘 수 있습니다. ‘시청시간이 늘었으니 좋은 변화’라는 과거 결론을 그대로 가져오면 당시의 목표가 현재의 판단 기준이 되어 버립니다.3.3. Task Context: 과제의 브리핑Task Context는 과제의 맥락을 에이전트에게 브리핑하는 역할입니다. 과제가 진행되는 Jira 이슈를 에이전트가 직접 읽도록 합니다.
브리핑 자료: Jira 이슈의 본문과 댓글
기록 방식: 관찰 → 가설 → 검증 결과 → 기각된 가설 → 다음 질문을 댓글로 이어서 남김
읽는 시점: 에이전트가 분석 전에 읽고 과제의 목적·경과·지금 답할 질문을 파악
브리핑이 실제 분석을 어떻게 바꾸는지는 4장에서 과제 하나를 따라가며 살펴봅니다.4. 적용 결과: 같은 기준으로 분석하는 팀세 컨텍스트를 갖춘 뒤로는 A/B 실험 결과나 추천 지표를 누가 분석하든 같은 로그, 같은 집계 규칙, 같은 검증 절차에서 출발합니다. 실제 과제 하나를 따라가며 세 컨텍스트가 어떻게 함께 쓰였는지 보겠습니다. 수치나 식별 정보는 빼고 가상의 사례로 재구성했습니다.4.1. 과제 배경과 브리핑추천 모델에 영상 임베딩 정보(영상의 내용을 숫자 벡터로 표현한 값)를 새 입력 피처로 추가했을 때 기존 방식보다 추천 성능이 개선되는지 확인하는 과제가 있었습니다. 과제 내용은 Jira 이슈에서 관리했고, 실제 사용자 트래픽을 나눠 두 방식을 비교하는 온라인 A/B 실험이 시작된 상태였습니다. 실험이 시작된 뒤 같은 이슈에 질문 두 개를 댓글로 남겼습니다. 지금까지의 결과로 실험을 계속할 가치가 있는지, 그리고 조정이 필요한지였습니다. 에이전트가 이슈에서 브리핑받은 맥락은 다음과 같습니다.

분석에 필요한 맥락
Jira에서 확인한 기록

왜 시작했는가?
영상 임베딩 피처 추가에 따른 추천 성능 비교

지금 어떤 단계인가?
온라인 A/B 실험 진행 중

지금 답할 질문은 무엇인가?
실험의 지속·조정 여부

이 브리핑 덕분에 분석은 지금까지의 결과로 효과를 어디까지 판단할 수 있고 다음에 무엇을 할지에 답하는 일이 됐습니다.
4.2. 분석: 지표 차이를 피처의 효과로 해석할 수 있는지 점검
에이전트는 CLAUDE.md의 순서대로 관련 카탈로그 문서를 읽고 현재 스키마를 다시 조회한 뒤, Persona의 분류에 따라 이 과제를 ‘A/B 효과’ 유형으로 잡았습니다. 설계에서는 주요 지표와 보조 지표를 나누고, 완전히 관측된 날만 분석 기간으로 삼았으며, 실험 전 기간의 데이터로 사용자 간 편차를 보정했습니다. 원래 활동량이 다른 사용자가 두 집단에 섞여 생기는 차이를 줄이기 위해서입니다.
함정 점검 단계에서는 연휴, 대조군 모델 교체, 이상치, 극단 사용자, 실험군 배분의 등을 확인했습니다. 점검 결과 소수의 이상치 행을 제외한 것 외에는 비교 조건을 바꿀 요인이 없었습니다. 어느 쪽 숫자가 높은지와, 그 차이를 피처의 효과로 해석할 수 있는지를 구분해 확인한 것입니다. 분석은 지표별로 SQL과 계산, 노트를 나눠 진행했고, 모듈마다 결과를 다시 검증하는 단계를 거쳤습니다.
4.3. 중간 결론과 후속 분석
중간 분석의 결론은 “관측한 범위에서 손해는 확인되지 않았지만, 이득도 확정하지 못했다” 였습니다. 에이전트는 관측 기간을 늘린 뒤 미리 정한 규칙으로 판정하자고 제안했고, 아직 답하지 못한 질문도 따로 적었습니다.
사람에게 검토받은 분석결과는 Jira 댓글로 과제에 에이전트가 기록해둡니다.
```
