Confluence와 Jira에 흩어진 문서를 증분으로 모으고, 검색에 쓸 수 없는 JSON을 Markdown으로 바꾸고, 이미지에는 대체 텍스트를 붙였습니다. 이미지가 보이지 않던 문제는 거기서 답이 됐습니다.

### 벡터 검색만으로는 부족했다

처음 떠올린 건 전통적인 RAG 구조였습니다. 문서를 잘게 잘라 임베딩해두고, 질문과 가까운 청크를 꺼내 모델에게 넘기는 방식입니다. 그런데 사내 질문에 대입해 보니 이 구조로는 부족했습니다.

“공통 게이트웨이에 필터를 하나 추가하려면?”의 답은 가이드 문서, 요청 프로세스 문서, 과거 Jira 이슈에 등에 조금씩 나뉘어 있는데, 벡터 검색은 비슷한 청크를 꺼내줄 뿐 그 조각들이 서로 어떤 관계인지는 알려주지 않습니다. 조각을 잇는 일이 매번 모델의 추측으로 남고, 추측에 기댄 답은 틀리기 쉽습니다.

필요한 건 **“비슷한 문서”** 가 아니라 **“이 개념이 어디에서 어떻게 이어지는지**”였습니다.

### LightRAG란 무엇인가

이 문제의식에 맞는 접근이 GraphRAG였습니다.

문서에서 개념(Entity)과 관계(Relation)을 미리 뽑아 지식 그래프로 만들어 두고, 검색할 때 그래프를 따라 관련 개념까지 함께 끌어오는 방식입니다.

문서를 넣는 시점에 “공통 게이트웨이”라는 개념과 “라우팅 요청 프로세스”라는 개념이 연결돼 있다는 것을 그래프로 만들어 두면, 검색 시점에는 그 연결을 따라가기만 하면 됩니다. 조각을 잇는 일을 매 질문마다 모델의 추측에 맡기는 대신, 인덱싱할 때 한번만 해두는 것입니다.

GraphRAG 계열로 저희가 고른 것이 LightRAG입니다. LightRAG는 GraphRAG 방식을 경량화한 오픈소스 프레임워크로, 문서에서 Entity/Relation을 추출해 지식 그래프를 구성한 뒤 그래프 탐색과 벡터 검색을 결합합니다.

동작을 요약하면 문서를 넣으면 LightRAG가 토큰 단위로 청킹하고, 각 청크를 LLM에 넘겨 Entity와 Relation을 추출해 그래프를 쌓습니다. 그리고 Entity, Relation, 청크 원문 세 갈래를 각각 임베딩해 둡니다.

질문이 들어오면 LLM이 질문에서 키워드를 추출하고, 그 키워드로 세 벡터 인덱스와 그래프를 함께 탐색해 결과를 합칩니다.

### LightRAG에 문서 넣고 검색하기

#### LightRAG에 문서 넣기

파이프라인의 마지막 단계는 정제된 문서를 LightRAG에 업로드하는 것입니다. 여기서는 LightRAG의 동작 방식인 갱신 방식과 비동기 인덱싱 두 가지를 고려했습니다.

LightRAG의 업로드 API에는 upsert가 없어서, 같은 ID로 다시 올리면 갱신되는 게 아니라 “duplicated”로 조용히 무시됩니다. 하루 세 번 문서를 증분으로 밀어 넣는 저희 파이프라인에서는 수정본이 그대로 버려지는 셈이라, 갱신을 삭제 → 삭제 완료 대기 → 재업로드 3단계로 풀었습니다. 삭제 역시 비동기라 요청 접수가 곧 완료는 아니기 때문에, 문서 목록을 재조회해 실제로 사라진 것을 확인한 뒤 재업로드합니다.

인덱싱도 비동기입니다. 업로드가 성공해도 뒤에서 도는 Entity 추출이 LLM 호출 한도(429)에 걸리면 문서는 failed로 남아, 파이프라인은 성공했는데 검색에서는 빠진 문서가 생깁니다. 그래서 인덱싱이 끝날 시점에 실패 문서를 조회해 Slack으로 알리고, 재처리 API를 자동으로 트리거하는 점검 스케줄을 돌리고 있습니다.

#### LightRAG에 검색하기

LightRAG에는 검색 API가 두 가지 있습니다. 검색하고 답변까지 생성해주는 /query, 그리고 검색된 Entity/Relation/청크를 원시 데이터로 돌려주는 /query/data 입니다.

에이전트에게 서빙하는 MCP에서는 /query/data만 씁니다. LightRAG에게 답변을 만들게 하지 않습니다.

저희가 구현하는 건 챗봇이 아니라 에이전트가 쓰는 검색 도구(MCP)입니다. 답변을 만드는 건 도구를 쓰는 에이전트의 몫이고, 도구가 할 일은 좋은 근거를 돌려주는 것입니다. 이 근거를 에이전트가 어떻게 받아 쓰는지 MCP로 서빙하는 이야기는 3편에서 풀어낼 예정입니다.

### LightRAG 품질을 높이기 위한 노력들

#### 개선 1 : 노이즈 Entity 걷어내기

기본 설정으로 사내 문서를 인덱싱하고 그래프를 열어봤을 때 처음 마주한 건, 지식이 아닌 대다수의 노이즈였습니다. 노이즈 유형 예시는 아래와 같습니다.

![](https://images.gogumang.com/7f521fb709/05.png)

날짜와 이슈 번호가 수백 개의 노드로 태어나 그래프를 부풀리고, 같은 사람이 표기별로 다른 노드로 흩어졌습니다. 원인은 크게 두 가지였습니다. LightRAG의 기본 entity type은 범용 문서를 전제로 하고 있어 Confluence/Jira에 흔한 날짜·채번 같은 구조적 데이터를 거를 기준이 없었고, 저희가 사용한 경량 모델은 분류가 모호하면 data나 UNKNOWN 타입으로 일단 뽑고 보는 경향이 있었습니다. 그래서 Entity 추출 프롬프트를 두 가지 방향으로 수정했습니다.

**1️⃣ Entity Type을 사내 문서에 맞게 재정의**

* 기본 타입 셋은 Creature, NaturalObject 처럼 픽션, 일반 텍스트까지 겨냥한 범용 구성인 데다 LLM이 판단이 서지 않으면 type을 즉석에서 만들어냅니다.

```
Person, Organization, Service, Concept, Method, Process, Tool, Event, Issue, Project, Location, Artifact
```

* 위와 같이 사내 문서에 맞는 Entity type으로 재정의하고, 여기에 포함되지 못하면 추출하지 않도록 지시했습니다. 원래 프롬프트의 “분류 불가면 Other로” 폴백이 노이즈의 통로였기 때문입니다.

**2️⃣ 한영 혼용 인물 규칙**

* 같은 사람이 소피, sofie, 소피(sofie) 처럼 여러 표기로 등장해도 별도 Entity로 생성하지 않고 \[영문 이름\] \[한글 이름\] 대표 표기 하나로만 추출하도록 명시했습니다.

개선 후 전체 노드는 42%로 줄었고, 특히 노이즈 노드(data/UNKNOWN 타입)은 86%감소했습니다.

#### 개선 2 : 프롬프트 사내 도메인 특화

Entity 추출만이 아니라, LightRAG가 인덱싱과 검색 곳곳에서 쓰는 프롬프트들도 모두 범용 기준으로 짜여 있습니다. 사내 도메인에 맞게 함께 손봤습니다.

**1️⃣ 키워드 추출**

* LightRAG의 검색은 질문에서 키워드를 뽑는 LLM 호출로 시작합니다. 사내 Confluence/Jira 기반 RAG 시스템임을 role에 명시해 질문을 사내 기술 문서 관점으로 해석하게 하고, 질문에 없는 단어를 키워드로 지어내지 않도록 막았습니다.

**2️⃣ Few-shot 예시 교체**

* 모델은 few-shot 예시의 패턴을 모방하는데, 기본 예시는 영문 픽션/뉴스/학술 텍스트라 사내 시스템/팀/구조를 가르치지 못합니다. Entity 추출 예시는 사내 시나리오 4건으로, 키워드 추출 예시는 사내 기술 질의 5건으로 전면 교체했습니다.

**3️⃣ System Prompt 간소화**

* 경량 모델은 긴 프롬프트의 중간에 있는 지시를 흘리는 경향이 있습니다(lost-in-the-middle). 규칙이 쌓이면서 프롬프트가 길어지자 실제로 중간의 지시를 놓치기 시작했습니다. 구조를 압축하여 모델이 끝까지 읽게 쓰도록 간소화했습니다.

여기까지의 프롬프트 개선으로 LightRAG 검색의 정확도(correctness)는 76%에서 84%로 올랐습니다.

이 외에도 가져올 후보 수(top_k, chunk_top_k), 인덱싱에 쓸 LLM 모델, 임베딩 모델 같은 설정들도 조합을 바꿔가며 테스트와 평가를 반복했고, top_k=40 / chunk_top_k=20, 경량 모델 인덱싱으로 정확도와 비용이 모두 감당되는 설정으로 운영하고 있습니다.

여기까지가 LightRAG를 도입하고 다듬어 온 과정입니다. 그런데 사내 문서로 정확히 답하려면 두 가지를 알아야 합니다. 무엇에 대한 문서인지, 그리고 어디에 놓인 문서인지. LightRAG가 채워준 것은 앞쪽입니다. 다음은 뒤쪽을 채우는 Navigator 이야기입니다.

### Navigator란 무엇인가

LightRAG를 얹고 검색은 확실히 좋아졌습니다. 그래도 틀리는 질문이 남았습니다. 후보를 못 찾은 것도, 근거가 부족한 것도 아니었습니다. 의미가 닮은 문서가 여럿일 때, 그중 어느 것이 맞는지를 **의미로는 가려낼 수 없었습니다.**

둘을 갈라놓는 단서는 본문이 아니라 **문서가 놓인 자리**에 있었습니다. Confluence의 어느 폴더 아래에 있는지, Jira의 어느 Epic에 매달려 있는지 같은 것들입니다. 다행히 이건 추측할 필요가 없는 값입니다. Confluence의 트리도 Jira의 계층도 누군가 손으로 정리해 둔 것이라, 읽어오기만 하면 됩니다.

그 구조를 원본 그대로 옮겨 담고 따라 걷도록 만든 것이 Navigator입니다. LightRAG가 채우지 못한 자리 정보를 여기서 보충합니다.

#### 제목이 같고 자리만 다른 문서

사내에는 “등록 라우팅 목록”이라는 페이지가 두 개 있습니다. 하나는 “01. B2C API 게이트웨이” 아래, 다른 하나는 “01–1. B2B API 게이트웨이” 아래에 있습니다. 앞 번호를 떼면 이름이 같고 내용도 유사합니다. 다른 건 놓인 자리뿐입니다.

![](https://images.gogumang.com/7f521fb709/06.png)

*두 게이트웨이 폴더에 하나씩 있는 등록 라우팅 목록*
> *Query : B2C 게이트웨이의 라우팅 목록 알려줘*

실제로 이 질의에서 답이 틀렸습니다. B2C 게이트웨이 쪽 라우팅을 물었는데, B2B 게이트웨이 아래 있는 목록을 근거로 답이 돌아왔습니다.

Jira에서도 비슷한 일이 생깁니다.
> *Query : 사내 Agentic RAG 구축 프로젝트에서 진행 중인 이슈 알려줘*

위 질문에 필요한 건 이슈 몇 건의 본문이 아니라, 그 이슈들이 어느 Epic 아래에 매달려 있는지입니다. 하위 작업 하나만 떼어놓고 보면 그게 전체에서 어디쯤인지 알 수 없습니다.

여기까지가 Navigator가 푸는 문제에 대한 내용이었습니다. 이제 남은 건 Navigator를 실제로 운영하기 위한 이야기입니다.

* 구조를 구조인 채로 어떻게 저장할 것인가
* 잘라낸 조각이 제자리를 어떻게 기억하게 할 것인가
* 팀 하나에서 전사로 늘리면 무엇이 무너지는가

#### 구조를 구조인 채로 어떻게 저장할 것인가

저장소로 벡터 DB를 쓸 수도 있었습니다. 청크를 벡터로 넣고 유사도로 꺼내는 일은 벡터 DB만으로 가능하지만 벡터 DB는 문서 사이의 관계를 담지 않습니다. 그래프 DB는 관계를 데이터의 일부로 저장하므로 벡터 DB가 아니라 그래프 DB를 선택했습니다.

Neo4j는 벡터 인덱스도 함께 지원하기 때문에 벡터로 청크를 뽑고 같은 쿼리에서 부모 페이지로 거슬러 올라가는 일이 가능합니다. 계층 탐색과 의미 검색을 서로 다른 저장소로 나눌 필요가 없었습니다.

데이터 모델은 원본을 거의 그대로 옮겼습니다. 추상화하거나 재구성하지 않고, Confluence에서 보이는 트리와 Jira에서 보이는 계층이 그래프에도 똑같이 살아 있도록 했습니다.

![](https://images.gogumang.com/7f521fb709/07.png)

*원본 계층을 그대로 옮긴 Neo4j 데이터 모델*

#### 잘라낸 조각이 제자리를 어떻게 기억하게 할 것인가

청킹(chunking)은 긴 문서를 검색 단위로 잘라 두는 작업입니다. 검색은 문서 전체가 아니라 이 조각 단위로 이뤄집니다.

문서를 통째로 임베딩할 수는 없었습니다. 임베딩 모델에는 입력 토큰 한도가 있고, 저희가 쓴 모델에서는 한도를 넘긴 뒷부분이 그냥 잘려나갑니다. 본문은 그대로 저장되는데 벡터에는 앞부분만 담기는 겁니다. 조회하면 전체가 보이니 눈으로는 멀쩡한데, 뒷부분 내용으로는 검색이 안 되는 상태가 됩니다. 한도 안에 들어가더라도 문제는 남습니다. 서로 다른 주제의 섹션 열 개가 벡터 하나로 뭉개지면, 그중 한 섹션을 묻는 질문과의 유사도가 오히려 낮아질 수 있습니다.

아래는 코사인 유사도를 직접 측정했을때의 결과 일부입니다. 페이지 전체를 임베딩한 벡터와, 같은 문서를 잘라 만든 청크 중 질문과 가장 가까운 하나를 비교했습니다.

![](https://images.gogumang.com/7f521fb709/08.png)

차이는 0.07에서 0.23로 전부 청크쪽이 높았습니다. 다만 이건 간이 비교입니다. 로컬 임베딩 모델로 청킹 효과만 봤고, 청크 쪽은 여러 조각 중 최댓값이라 후보가 많은 만큼 유리하기도 합니다.

자르는 기준은 헤딩으로 잡았습니다. 사내 문서는 대체로 H1/H2/H3로 목차가 잡혀 있고, 그 경계가 곧 주제의 경계이기 때문입니다. 섹션이 3,000자를 넘으면 먼저 문단 경계에서 나누고, 그래도 넘치면 줄과 단어 순으로 내려가며 다시 잘랐습니다. 이때 잘린 조각끼리는 겹치지 않게 저장하되, 임베딩할 때만 직전 조각의 끝 200자를 앞에 붙여 경계에서 문맥이 끊기지 않게 했습니다. 물론 실제 문서는 그렇게 정연하지 않아서, 헤딩이 아예 없거나 제목만 있고 본문이 없는 경우를 위한 예외 처리를 여럿 붙여야 했습니다.

Jira는 다르게 잘랐습니다. 이슈에는 헤딩이 없고, 대신 본문과 댓글이라는 자연스러운 경계가 있습니다. 짧은 이슈는 통째로 한 조각으로 두고, 길어지면 본문 하나와 댓글 여러 개로 나눕니다. 같은 파이프라인이지만 문서의 생김새가 다르면 자르는 법도 달라야 했습니다.

문제는 문서를 쪼개면 조각이 자기가 어디에서 떨어져 나왔는지를 잊는다는 것입니다. “1. 개요”라는 제목의 청크는 사내에 수백 개가 있습니다.

그래서 각 청크의 임베딩 입력 앞에 계층 경로를 붙였습니다.

```
공통플랫폼개발팀 > 01. B2C API 게이트웨이 > 1-5. 등록 라우팅 목록

[섹션 본문]
```

이 경로 한 줄 덕분에 청크가 단독으로 검색되어도 자기 위치를 들고 다닙니다. 앞에서 이야기한 등록 라우팅 목록 두 개도, 청크 단계에서 이미 어느 게이트웨이 아래인지가 구분됩니다.

처음에는 이 경로를 본문에 그대로 심어 저장했습니다. 그랬더니 문서를 다시 읽을 때 청크마다 같은 경로가 반복돼 본문이 지저분해졌습니다. 검색에는 필요하고 조회에는 방해가 되는 정보라, 앞의 오버랩과 같은 방식으로 갈랐습니다. 경로도 임베딩할 때만 붙입니다.

#### 팀 하나에서 전사로 늘리면 무엇이 무너지는가

팀 하나를 대상으로 할 때는 문제가 없었습니다. 범위를 넓히자 첫 실행에서 한 프로젝트의 적재가 1시간 30분 넘게 진행되지 않아 사실상 멈췄습니다. 노드를 저장할 때 쓰는 키에 인덱스가 없어 노드가 늘어날수록 레이블 전체 스캔이 됐기 때문입니다. 여기에 임베딩할 텍스트를 한 번에 다 메모리에 올리던 것이 겹쳤습니다. 메모리는 100%에 닿았고 서버가 내려갔습니다. 문서가 수천 건일 때는 드러나지 않던 설계가 문서 17만 건에서 그대로 드러난 셈입니다.

범위를 넓히던 중에 쓰던 모델의 지원 종료가 예고되어 있어 임베딩 모델도 변경해야 했습니다. 임베딩은 모델이 다르면 벡터 공간도 달라지기 때문에 일부만 바꿔 끼울 수가 없습니다. 전 문서를 변경 모델로 다시 임베딩해야 합니다.

전사 확장을 위해 크게 3가지 방향으로 개선했습니다.

**1️⃣ 인덱스 추가 (MERGE 키 속성 인덱스)**

```
issue_id, issue_key, project_name, issuechunk_id, page_id, pagechunk_id, space_key
```

* 속성 인덱스가 없다면 노드가 많아질수록 전체 라벨 스캔(O(n²))이 되어 대량 적재가 매우 느립니다. 따라서 적재를 시작하기 전에 속성 인덱스를 만들었습니다. 속성 인덱스는 관계형 DB의 인덱스와 같은 역할을 합니다. id가 이 값인 노드를 찾을 때, 같은 라벨을 전부 훑는 대신 바로 짚어냅니다.

**2️⃣ 분할 적재 (per-team batching)**

* Confluence Space와 Jira Project 단위로 끊어 처리합니다. 한 번에 메모리에 올라오는 건 한 팀 분량이고, 팀이 몇이든 그 상한은 그대로입니다. 팀 안에서도 청크 500개씩 끊어 임베딩하고 바로 적재하니, 벡터가 메모리에 머무는 양도 함께 고정됩니다.

**3️⃣ Content 해싱 (증분 스킵)**

* 데이터 파이프라인의 증분 수집이 걸러주는 건 “언제 수정됐는가”까지입니다. 수정 시각만 바뀌고 내용은 그대로인 문서도 적지 않습니다. 그래서 문서마다 해시를 떠 둡니다. 임베딩에 넣을 최종 텍스트에 모델 이름을 붙여 만든 값인데, 해시가 같으면 임베딩도 청크 재작성도 건너뛰고 메타데이터만 갱신합니다. 모델 이름이 섞여 있으니, 모델을 바꾸면 해시가 한꺼번에 달라져 재임베딩을 따로 지시할 필요가 없습니다.

개선 후 Navigator 적재 시간은 기존 대비 약 81% 단축, 메모리 사용률은 40% 감소되었습니다.

### 마치며

2편에서는 1편에서 다져둔 문서 위에 두 개의 리트리버를 얹었습니다. 의미로 찾는 LightRAG, 구조로 걷는 Navigator. 서로 대체하는 관계가 아니라, LightRAG가 “무엇에 대한 문서인가” 를 찾아내면 Navigator가 “어디에 놓인 문서인가” 를 확인하는 분업 관계입니다. 에이전트는 개념 지도로 후보를 좁히고, 계층 조회로 주변을 확인한 뒤, 필요한 원문만 읽어 답합니다. 키워드를 바꿔가며 헤매던 검색이 몇 번의 호출로 끝나게 된 이유입니다.

그리고 이 글에는 **“정확도 76% → 84%”** 같은 숫자가 등장했습니다. 이 숫자들은 어떻게 잰 걸까요? 검색 품질을 재는 평가 파이프라인과 LLM Observability, 그리고 두 리트리버를 하나의 MCP로 서빙하는 이야기가 3편입니다.

읽어주셔서 감사합니다.
