글. 심수현(Dante) / 전시개발팀

안녕하세요.

전시개발팀에서 여기어때 서비스를 개발하고 있는 단테입니다.

저희 팀은 레거시 API와 신규 API의 응답이 같은지 비교하기 위해 쉐도잉이라는 방법을 사용합니다.
> ***쉐도잉(Shadowing)이란?***
>
>
> *실제 요청을 신규 로직에도 보내 기존 로직과 결과를 비교하는 방식입니다. 사용자에게는 기존 로직의 결과를 전달하고 신규 로직의 결과는 검증에 사용합니다. 두 응답이 일치하지 않는다면 신규 로직에 잘못된 비즈니스 로직이 적용되었다고 판단할 수 있습니다.*

![](https://images.gogumang.com/361d8e1cc1/01.gif)

쉐도잉을 처음 도입한 이야기는 이전에 주드가 작성한 [전시 API 서비스 전환기 Part 2](https://techblog.gccompany.co.kr/전시-api-서비스-전환기-part-2-8a850765ac49)에 있으니 이 글을 읽기 전에 먼저 보셔도 좋을 것 같습니다.

저희는 클라이언트가 쓰는 API를 주로 만들지만 사용자 눈에는 보이지 않는 내부 개선 작업도 꽤 자주 합니다.

내부 구조 개선, 성능 개선, 리팩토링, 그리고 우리가 호출하는 외부 API의 동작이 바뀌어서 맞춰야 하는 작업까지요.

이런 작업은 겉으로 보면 달라진 게 없어야 정상입니다. 그래서 오히려 검증이 어렵습니다.

기능이 새로 생긴 게 아니니 QA를 요청하기도 애매하고 그렇다고 이런 작업이 있을 때마다 QA 일정을 잡을 수도 없었습니다.

결국 개발자가 직접 검증하고 배포하는 일이 반복됐습니다.

오늘은 그 검증을 어떻게 해왔고 무엇이 불편했고 지금은 어떻게 바꿨는지 이야기해 보겠습니다.

### 이번에 검증해야 했던 변경

최근에 가장 크게 검증이 필요했던 작업부터 소개하겠습니다.

전시 영역의 제휴점 상품 정보는 원래 원천 데이터에서 Kafka로 변경분을 받아 전시 쪽 MongoDB에 저장해 두고 읽는 구조였습니다.

오랫동안 잘 돌아간 구조였지만 다루는 상품이 늘어나면서 확장성에 대한 고민이 생겼고 증분이 전시 저장소까지 반영되는 사이의 지연 때문에 실시간성 이슈도 생겼습니다.

그래서 MongoDB를 거치지 않고 원천 데이터에서 제공하는 API를 직접 호출하도록 바꾸기로 했습니다.

말은 간단하지만 제휴점 리스트(PLP), 숙소 상세(PDP), 객실 리스트(ILP), 객실 상세(RDP), 달력 요금 처럼 가격과 재고를 보여주는 화면의 데이터 출처가 통째로 바뀌는 작업입니다.

사용자나 제휴점 고객 입장에서는 가격 변동이 없다면 어제 보던 가격과 오늘 보는 가격이 같아야 하는데 이걸 무엇으로 확인할지가 문제였습니다.

### 내부 테스트만으로는 부족했습니다

저희가 다루는 응답은 숙소, 객실, 날짜, 인원, 회원 등급, 할인이 얽혀 있어서 테스트 케이스로 만들 수 있는 조합이 실제 요청의 극히 일부에 불과했습니다.

테스트는 통과하는데 운영에서 어떤 숙소의 어떤 날짜에서만 가격이 다르게 나오는 식의 문제는 테스트로 잡히지 않았습니다.

그래서 이런 작업에도 쉐도잉을 씁니다.

방법은 단순합니다.

실제 요청이 들어오면 사용자에게는 기존 로직의 결과를 그대로 내려주고 내부의 별도 스레드에서 개선한 로직을 한 번 더 호출한 뒤 두 결과를 비교하는 방식입니다.

비교 대상은 경우에 따라 달랐습니다.

API 응답 전체를 비교할 때도 있었고 응답을 만들기 전 단계의 중간 객체를 비교할 때도 있었습니다.

어느 쪽이든 운영 트래픽을 그대로 테스트 데이터로 쓸 수 있다는 점이 가장 큰 장점이었습니다.

### 그런데 비교 결과를 읽는 건 사람이었습니다

비교 자체는 코드가 했습니다. 문제는 그다음입니다.

비교 결과는 로그로 남겼는데 예를 들어 PDP API를 V2에서 V3로(성능개선) 새로 만들 때 쓰던 쉐도잉 로그는 이런 모양이었습니다.

```
SHADOW_DIFF request placeId=100001, checkInOut=(2026-09-10, 2026-09-11), person=2, userId=null, membership=ELITE, hardBlock=null, platform=APP, channel=yeogi, display=10, channeling=false, channelCode=null
 field=pdp.roomInfoList[roomId=20011] v2Value=present v3Value=null
SHADOW_DIFF request placeId=100002, checkInOut=(2026-09-11, 2026-09-12), person=2, userId=null, membership=ELITE, hardBlock=null, platform=APP, channel=yeogi, display=10, channeling=false, channelCode=null
   field=pdp.roomInfoList[roomId=20012].stayInfo.discountRate v2Value=13 v3Value=4
```

(형식은 당시 코드 그대로이고 숫자는 설명을 위해 넣은 값입니다.)

이 로그를 어떻게 읽었는지 순서대로 따라가 보겠습니다.

![](https://images.gogumang.com/361d8e1cc1/02.gif)

**① 로그 조회**

먼저 서버에 접속해서 콘솔에서 로그를 조회합니다.

SHADOW_DIFF로 걸러내되 뒤에 이어지는 줄까지 같이 봐야 합니다. 불일치 필드마다 줄이 따로 찍혀서 한 건이 여러 줄에 걸쳐 있기 때문입니다.

![](https://images.gogumang.com/361d8e1cc1/03.png)

**② 한 줄 읽기**

그중 한 줄을 골라 읽습니다.

두 번째 건이라면 10001번 숙소의 20011번 객실에서 할인율이 V2에서는 13이고 V3에서는 4로 나왔으며 재고도 하나 차이가 났다는 뜻입니다.

![](https://images.gogumang.com/361d8e1cc1/04.png)

여기까지는 괜찮습니다.

**③ 요청 다시 조립**

막히는 건 그다음입니다.

첫 줄에 체크인 날짜와 인원과 회원 등급까지 찍혀 있기는 합니다. 하지만 이건 서비스 안에서 한 번 정리한 요약값이지 실제로 들어온 요청 그대로가 아닙니다.

재현하려면 이 값들을 보고 API의 쿼리 파라미터 이름과 헤더 형식에 맞춰 요청을 손으로 다시 조립해야 했습니다.

![](https://images.gogumang.com/361d8e1cc1/05.png)

**④ 직접 호출·재현**

조립한 요청으로 V2와 V3를 각각 호출해 보고 로그와 같은 값이 나올 때까지 재현을 시도했습니다.

![](https://images.gogumang.com/361d8e1cc1/06.png)

**⑤ 원인 비교**

재현이 되면 그제서야 V2 응답과 V3 응답을 나란히 놓고 어느 쪽이 맞는지와 왜 달라졌는지를 따져봤습니다.

![](https://images.gogumang.com/361d8e1cc1/07.png)

**⑥ 다음 줄로**

그리고 다음 줄로 넘어갑니다.

![](https://images.gogumang.com/361d8e1cc1/08.png)

한두 건이면 할 만했습니다.

하지만 트래픽이 많은 API에 쉐도잉을 붙이면 로그가 금방 쌓였고 그중 어떤 게 새로운 문제이고 어떤 게 방금 본 문제의 반복인지 구분하는 것부터 일이었습니다.

아주 괴로운 작업이었을 텐데 사실 저는 해 본 적이 없습니다. 괴로울 게 뻔히 보여서 프로젝트를 시작하기 전에 쉐도잉부터 개선해 보겠다고 나섰거든요.

### 로그로는 답할 수 없는 질문들

로그 한 줄의 원인을 찾더라도 검증 전체에 대해서는 이런 질문이 남습니다.

* 비교한 요청 중에 얼마나 다른가?
* 어떤 필드가 다른가?
* 어디까지 다른가? 한 필드만인가 응답 전체가 흔들리는가?
* 어떤 요청일 때 다른가?

이 질문에 답하려면 로그를 모아서 직접 세야 했습니다.

그런데 로그는 애초에 세기 좋은 모양이 아니었습니다.

* 일치한 요청은 로그에 남지 않았습니다. 분모가 없으니 몇 퍼센트가 다른지는 셀 수가 없었습니다.
* API마다 로그 모양이 달랐습니다. PLP와 PDP는 SHADOW_DIFF, RDP는 RDP_SHADOW_DIFF, ILP는 \[ILP-SHADOW-DIFF\]로 시작하고 담는 필드도 제각각이었습니다.
* 한 건이 여러 줄에 걸친 텍스트라 grep으로 걸러도 건수를 세거나 필드별로 묶기가 어려웠습니다.

통계를 낼 방법이 마땅치 않았고 한눈에 볼 대시보드도 없었습니다.

그래서 솔직히 말하면 로그를 보면서 눈에 띄는 것부터 고치는 수밖에 없었습니다.

고치고 나서 다시 로그를 봤을 때 조용하면 괜찮아진 것 같다고 판단했는데 사실 그게 정말 괜찮아진 건지 그 시간에 해당 요청이 안 들어온 건지는 알 수 없었습니다.

작업 하나를 검증하는 데 개발자가 붙어서 로그를 계속 들여다봐야 했으니 리소스도 생각보다 많이 들었습니다.

### 오케스트레이션이냐 대시보드냐

이 질문들에 답하려면 쉐도잉 결과를 모아서 볼 곳이 필요했습니다.

처음 떠올린 건 오케스트레이션 방식이었습니다.

![](https://images.gogumang.com/361d8e1cc1/09.gif)

*Twitter Diffy Flow (출처: <https://github.com/opendiffy/diffy>)*

Twitter가 공개한 [Diffy](https://github.com/twitter-archive/diffy)처럼 애플리케이션 앞에 프록시를 두고 실제 요청을 기존 서비스와 신규 서비스에 똑같이 보낸 뒤 두 응답을 한곳에서 비교하는 방식입니다.

재미있는 건 Secondary입니다. 기존 서비스를 한 벌 더 띄워서 기존끼리 비교해 보면 코드가 같아도 매번 달라지는 값이 드러나는데 Diffy는 이걸 노이즈로 보고 신규와 기존의 차이에서 걸러냅니다.

![](https://images.gogumang.com/361d8e1cc1/10.png)

*Twitter Diffy 대시보드 (출처: <https://github.com/opendiffy/diffy>)*

이렇게 하면 애플리케이션 코드에 쉐도잉 코드를 한 줄도 넣지 않아도 되고 어떤 API든 같은 방식으로 검증할 수 있습니다. 욕심이 나는 구조였습니다.

그런데 저희 상황에 바로 가져오기에는 걸리는 게 있었습니다.

* 이번에 검증할 신규 로직은 따로 배포된 서비스가 아니었습니다.
  같은 애플리케이션 안에서 Mongo 대신 원천 API로 응답을 조립하는 코드 경로라서 프록시가 요청을 나눠 보낼 대상이 없었습니다.
* 프록시와 비교 결과를 모을 수집 서버와 저장소를 새로 만들고 배포해야 했습니다.
  당장 필요한 건 “얼마나 같은가”를 보는 것이었는데 그 전에 해야 할 일이 너무 많았습니다.
* 무엇을 같은 응답으로 볼지는 도메인마다 다릅니다.
  매번 달라지는 값을 어떻게 다룰지는 결국 애플리케이션이 가장 잘 알고 있었습니다.

반면 Grafana와 Prometheus와 Loki는 이미 사내에서 쓰고 있었습니다.

애플리케이션이 메트릭과 로그만 제대로 남기면 인프라를 하나도 바꾸지 않고 대시보드를 만들 수 있었습니다.

그래서 단계를 나누기로 했습니다.

* Phase 1: 쉐도잉 실행은 애플리케이션 안의 공통 라이브러리가 맡고 결과는 메트릭과 로그로 남겨 Grafana 대시보드로 봅니다.
* Phase 2: 오케스트레이션 방식으로 넘어갑니다.

다만 Phase 1을 만들면서도 나중에 오케스트레이션으로 넘어갈 때 버리지 않도록 몇 가지는 처음부터 맞춰 두었습니다.

* 비교 대상 이름을 V2·V3나 Mongo·원천 API가 아니라 primary와 candidate로 정했습니다. 누가 이 비교를 만들었는지도 이벤트에 producer로 남깁니다. 나중에 프록시가 비교를 만들어도 같은 형식으로 들어올 수 있게 하려는 것입니다.
* 요청은 method와 URI와 헤더까지 재현할 수 있는 형태로 남깁니다. 지금은 불일치를 재현하는 데 쓰지만 나중에는 요청을 다시 보내는 입력으로도 쓸 수 있습니다.

### 대시보드를 만들기까지 한 일들

대시보드라고 하면 Grafana에 패널 몇 개를 올리면 끝날 것 같지만 숫자를 믿을 수 있게 만드는 데 오히려 시간이 더 들었습니다.

Phase 1에서 어떤 일들을 했는지 정리해 보겠습니다.

**무엇을 셀지부터 정했습니다**

예전 쉐도잉은 대부분 차이가 있을 때만 로그를 남겼습니다.

일치율을 계산하려면 분모가 필요한데 그 분모가 없었던 겁니다.

그래서 쉐도잉 실행 건수와 판정별 건수를 나누어 기록하도록 바꿨습니다.

reporter.executed()는 오류를 포함한 실행 건수를 세고 reporter.report()는 MATCH·DIFF·ERROR 판정을 남깁니다.

집계 단위도 정해야 했습니다. 한 요청 안에서 객실 열 개가 달라도 DIFF는 한 건으로 세고 어느 객실의 어느 필드가 달랐는지는 diff 목록에 따로 담습니다. 요청 단위로 세야 “전체 요청 중 몇 퍼센트가 같은가”라는 질문에 바로 답할 수 있기 때문입니다.

비교하지 못한 요청은 ERROR로 따로 뺐습니다.

이걸 분모에 넣으면 비교를 못 한 요청 때문에 일치율이 내려가고 빼기만 하면 실패가 숨어버립니다. 그래서 일치율 계산에서는 빼고 대시보드에는 ERROR 건수를 옆에 따로 띄웠습니다.

그래서 대시보드 맨 위에는 이 네 숫자가 나란히 있습니다.

![](https://images.gogumang.com/361d8e1cc1/11.png)

*일치율, 불일치, 쉐도잉 실행, ERROR*

기존 로직은 항상 primary 신규 로직은 항상 candidate입니다. 전환 중에 어느 쪽을 사용자에게 내려주든 이 이름은 바뀌지 않습니다. 이름이 서빙 쪽을 따라 바뀌면 같은 그래프가 전환 시점에 뜻이 뒤집히기 때문입니다.

**메트릭과 로그의 역할을 나눴습니다**

숫자는 메트릭으로 원인은 로그로 보기로 했습니다.

메트릭에는 셀 수 있는 것만 담았습니다.

* shadowing_executed: 오류를 포함한 쉐도잉 실행 건수
* shadowing_result: 판정별 건수 (MATCH, DIFF, ERROR)
* shadowing_duration, shadowing_side_duration: 전체 처리 시간과 기존·신규 각각의 소요 시간
* shadowing_field_diff: 필드별 불일치 수

대시보드의 일치율은 이 메트릭으로 이렇게 계산합니다.

```
sum(increase(shadowing_result{result="MATCH"}[$__range]))
  / sum(increase(shadowing_result{result=~"MATCH|DIFF"}[$__range]))
```

실제 값이나 숙소 ID는 메트릭 라벨에 넣지 않았습니다.

라벨 값이 늘어날수록 시계열이 폭발적으로 늘어나기 때문입니다.

필드별 불일치를 셀 때 필드 이름을 정규화하고 종류에 상한을 둔 것도 같은 이유입니다.

대신 어떤 요청에서 어떤 값이 달랐는지는 SHADOW_EVENT 로그 한 줄에 JSON으로 담았습니다.

대시보드의 원본 이벤트와 요청 목록 패널은 Loki에서 이 로그만 골라 JSON을 풀어서 보여줍니다.

```
{k8s_deployment_name=~"$application"} | scope_name="SHADOW_EVENT" |~ "result.:.(DIFF|ERROR)" | json
```

응답 원문 전체는 로그에 싣지 않았습니다.

로그가 너무 커지기도 하고 대부분은 diff 목록만으로 원인을 찾을 수 있었습니다.

대시보드에서는 두 가지가 나란히 붙어 있습니다.

왼쪽 필드별 불일치 표는 메트릭으로 그리고 오른쪽 원문은 Loki 로그에서 가져옵니다.

![](https://images.gogumang.com/361d8e1cc1/12.png)

**재현할 수 있는 요청을 남겼습니다**

예전 로그의 가장 큰 불편이 요청 정보가 placeId 하나뿐이었다는 점이었습니다.

처음에는 서비스에 넘어온 파라미터로 요청을 다시 조립해서 담았습니다.

그런데 이렇게 만든 요청은 실제 API 요청과 조금씩 어긋났습니다.

재현하려고 그대로 호출했는데 다른 결과가 나오면 소용이 없습니다.

그래서 지금은 GET 요청이면 들어온 요청의 URI와 쿼리 스트링과 헤더를 그대로 캡처해서 이벤트에 담습니다.

뒤에서 볼 대시보드 요청 목록의 URI를 복사해서 그대로 호출하면 같은 조건이 재현됩니다.

헤더는 회원 등급처럼 결과에 영향을 주는 것만 골라 담았고 사용자 ID 같은 민감 정보는 넣지 않았습니다.

대시보드 요청 목록에는 이렇게 보입니다. 요청 URI와 회원 등급 헤더와 불일치 필드가 한 줄에 같이 나옵니다.

![](https://images.gogumang.com/361d8e1cc1/13.png)

**양쪽 소요 시간을 공정하게 재야 했습니다**

처음 대시보드를 띄웠을 때 소요 시간 그래프에는 신규 로직 선 하나만 있었습니다.

기존 로직은 사용자에게 내려줄 때 이미 실행했고 쉐도잉에서는 그 결과를 재사용하기 때문에 잴 시간이 없었던 겁니다.

이러면 신규가 빠른지 느린지 비교할 수가 없습니다.

그래서 호출부가 서빙할 때 잰 시간을 primaryServed(결과, servedMillis)로 함께 넘기도록 API를 늘렸습니다.

시간을 넘기지 않으면 0ms가 아니라 “미측정”으로 두고 그래프에서 뺍니다.

0ms로 넣으면 기존 로직이 엄청 빠른 것처럼 보이니까요.

이렇게 바꾼 뒤에야 그래프에 선이 두 개 나오기 시작했습니다.

![](https://images.gogumang.com/361d8e1cc1/14.png)

**대시보드 화면을 설계했습니다**

화면은 바로 만들지 않고 오버뷰형과 필드 분석형과 이벤트 탐색형과 상황판형까지 시안 네 가지를 먼저 만들어 비교한 뒤 지금의 구성으로 정했습니다.

지금 관제용 대시보드에는 패널이 12개 있습니다. 위에서 아래로 “전체가 괜찮은가 → 어느 대상이 문제인가 → 어느 필드가 문제인가 → 어떤 요청이었나” 순서로 좁혀 내려가게 배치했습니다.

비교 대상은 대시보드에 고정해 두지 않고 메트릭에서 읽어오는 변수로 만들었습니다.

새 API에 쉐도잉을 붙이면 대시보드를 고치지 않아도 대상 목록에 자동으로 나타납니다.

실제로 캘린더 API를 맡은 동료가 같은 라이브러리로 쉐도잉을 붙였을 때 대시보드는 한 줄도 고치지 않았는데 대상 목록에 캘린더 항목들이 올라왔습니다.

기업 요금 요청은 -CORPORATE를 붙여 따로 나눠 보는 것도 동료가 대상 이름만 정해서 해결했습니다.

![](https://images.gogumang.com/361d8e1cc1/15.png)

필드별 불일치 표는 관제 화면에서 상위 100개만 보여줍니다.

전체를 뒤져봐야 할 때를 위해 개수 제한 없이 정규식으로 필드를 검색하는 탐색용 대시보드를 하나 더 만들었습니다.

화면은 개발 서버에 올리기 전에 Prometheus와 Loki와 Grafana를 docker compose로 로컬에 띄워서 쉐도잉 이벤트가 패널에 찍히는 것까지 먼저 확인했습니다.

**노이즈를 걷어내야 숫자를 믿을 수 있었습니다**

대시보드를 켜고 필드별 불일치 순위를 들여다보니 상당수가 진짜 차이가 아니었습니다.

* 쿠폰 문서 ID: 할인액이 같은 쿠폰 문서가 여러 개면 조회 순서에 따라 어느 문서가 뽑히는지가 갈렸습니다.
* 실시간 카운트다운: 계산한 시각이 다르니 항상 어긋났습니다.
* 휴폐업 숙소와 지난 날짜 요청: 어느 쪽도 팔 수 없는 상품인데 한쪽만 빈 객실을 만들어 차이가 쌓였습니다. PLP에서는 한 요청의 숙소 30개 중 17\~25개가 이 이유로 어긋나기도 했습니다.
* 정률 특가의 1원 반올림: 계산 순서 차이로 1원이 갈리고 거기서 파생되는 할인율이 1%p씩 갈렸습니다.

이런 차이는 비교기에서 걷어냈습니다. 다만 기준은 엄격하게 잡았습니다.

사용자 화면에 나가지 않거나 실행할 때마다 달라지는 값만 뺐고 금액 필드는 끝까지 비교합니다.

1원 반올림처럼 조건을 걸어 흡수한 차이는 몇 건을 흡수했는지 메트릭으로 따로 셉니다.

흡수한 게 너무 많아지면 그것도 신호이기 때문입니다.

![](https://images.gogumang.com/361d8e1cc1/16.png)

이렇게 노이즈를 하나씩 걷어내고 다시 일치율을 보는 과정을 반복하면서 대시보드의 숫자가 조금씩 믿을 만해졌습니다.

### 완성된 대시보드

이렇게 만든 대시보드를 위에서부터 살펴보겠습니다.

![](https://images.gogumang.com/361d8e1cc1/17.png)

맨 위에는 일치율, 불일치 수, 쉐도잉 실행 수, ERROR 수가 있습니다.

캡처 시점 기준으로 수십만 건을 비교했고 그중 불일치는 극히 일부라 일치율이 99.98%였습니다.

예전 같으면 “불일치 로그가 좀 있긴 한데 많지는 않아요” 정도로 말했을 상황을 이제는 숫자로 말할 수 있게 된 겁니다.

옆의 ERROR는 앞에서 설명한 것처럼 비교하지 못한 요청 수입니다. 일치율이 높아도 이 숫자가 크면 안심할 수 없습니다.

그 아래에는 대상별 일치율 추이가 있습니다.

ILP, PDP, RDP처럼 쉐도잉을 붙인 API를 나눠서 보니 전체 숫자에서는 안 보이던 차이가 보였습니다.

캡처에서는 RDP가 100%를 유지하는 동안 ILP와 PDP가 시간이 지나면서 조금씩 내려가는 게 보입니다.

(세로축이 99.97%에서 100% 사이라 기울기가 실제보다 가파르게 보이는 점은 감안해야 합니다.)

맨 아래 오른쪽은 기존 로직과 신규 로직의 소요 시간을 나란히 놓은 그래프입니다.

이번 작업은 저장소를 읽던 걸 API 호출로 바꾸는 일이라 응답이 같은지만큼이나 얼마나 느려지는지가 중요했습니다.

이 구간에서는 신규 쪽이 약 20ms이고 기존 쪽이 약 13ms 정도로 신규가 더 느렸습니다.

응답은 거의 다 같은데 성능은 차이가 있다는 걸 전환하기 전에 미리 알 수 있었던 겁니다.

### “어디가 다른데요?”까지 대시보드에서 끝내기

일치율이 떨어졌다는 것만으로는 뭘 고쳐야 할지 모릅니다.

그래서 대시보드 아래쪽은 원인을 좁히는 데 쓰도록 구성했는데 하나씩 살펴보겠습니다.

![](https://images.gogumang.com/361d8e1cc1/18.png)

왼쪽 위는 필드별 불일치 순위입니다.

어느 필드에서 차이가 몰리는지 먼저 보고 오른쪽의 원본 이벤트에서 실제로 기존 값과 신규 값이 어떻게 달랐는지 확인합니다.

이 원본 이벤트는 Loki에서 바로 가져옵니다.

예전처럼 서버에 접속해서 로그를 찾을 필요 없이 대시보드에서 필터를 걸면 해당 이벤트의 로그가 옆에 바로 뜹니다.

캡처에는 place\[10001\].products.20022.stay.displayPrice.discountRatePerDay의 기존 값이 13이고 신규 값이 4로 찍혀 있습니다.

어떤 숙소의 어떤 상품에서 어떤 할인율 필드가 달랐는지 여기서 바로 보입니다.

참고로 필드 목록 맨 위에 보이는 __overflow__는 실제 필드가 아닙니다.

필드 이름이 너무 많아지면 메트릭 저장 비용이 커지기 때문에 일정 개수를 넘어선 새 필드들을 묶어서 세는 ‘기타’ 칸입니다.

이 칸이 크다는 건 경로에 상품 ID처럼 계속 바뀌는 값이 섞여 있다는 신호라서 오히려 경로 정규화를 더 손봐야 한다는 힌트로 쓰고 있습니다.

아래쪽은 불일치나 오류가 난 요청 목록입니다.

예전 로그에 placeId 하나만 있어서 재현에 애를 먹었을 동료들에게는 이 표가 가장 반가운 화면이 아닐까 싶습니다.

요청 URI와 쿼리 파라미터, 회원 등급이 담긴 헤더, 불일치 필드가 한 줄에 같이 나오기 때문에 어떤 요청일 때 어떤 diff가 나는지를 찾으려고 조건을 바꿔가며 호출해 볼 필요가 없어졌습니다.

다른 대상도 한번 보겠습니다.

![](https://images.gogumang.com/361d8e1cc1/19.png)

캘린더 API는 날짜별 salePrice에서 차이가 났는데 목록을 보면 같은 숙소의 같은 날짜가 반복해서 걸리는 게 보입니다.

로그를 한 줄씩 읽었다면 같은 문제를 여러 번 보고 있는지도 몰랐을 것 같습니다.

### 매번 쓰던 코드는 라이브러리로 뺐습니다

대시보드를 만들려면 모든 쉐도잉이 같은 형식으로 결과를 내보내야 했습니다.

그런데 예전 쉐도잉 코드는 API마다 조금씩 달랐습니다.

샘플링 방식도, 비동기 실행 방식도, 비교 결과를 남기는 로그 형식도 각자 달랐습니다.

같은 ‘불일치’라는 단어를 쓰는데 의미가 조금씩 달랐던 셈입니다.

그래서 반복되는 부분을 공통 라이브러리로 묶었습니다.

PLP를 예로 들어 예전 코드와 지금 코드를 나란히 놓고 보겠습니다.

참고로 두 코드가 검증한 변경은 다릅니다.

예전 코드는 PLP API를 V2에서 V3로 새로 만들 때 쓴 것이고 지금 코드는 이번 원천 API 전환에 쓰고 있는 것입니다.

그래도 같은 PLP 화면을 검증하는 쉐도잉이라 구조를 비교하기에는 충분하다고 봤습니다.

**예전: 어노테이션과 AOP로 만든 PLP 쉐도잉**

2025년 11월에 만든 PLP 쉐도잉은 컨트롤러에 어노테이션을 붙이면 AOP가 응답 뒤에 끼어드는 방식이었습니다.

흐름이 보이도록 여러 파일에서 핵심만 발췌했습니다.

```
// 1. 컨트롤러에 어노테이션을 붙이면
@ShadowComparison(targetPageType = "PLP")
@PostMapping
public AppPLPResponse postAppPLP(...) { ... }

// 2. Aspect가 응답이 나간 뒤에 끼어들어 샘플링하고 별도 스레드로 넘깁니다
@AfterReturning(pointcut = "@annotation(shadowComparison) && args(...)", returning = "ignored")
public void afterReturn(ShadowComparison shadowComparison, ..., AppPLPParameter request, ...) {
    if (!builderConfig.isShadowEnabled()) return;
    if (!shouldSample(rate)) return;
    CompletableFuture
        .runAsync(() -> shadowService.compareWithTarget(snapshot, shadowComparison.targetPageType()), shadowExecutor)
        .orTimeout(snapshot.timeoutMs(), TimeUnit.MILLISECONDS);
}
// 3. 서비스가 V2와 V3를 다시 호출해 숙소별로 비교하고
for (Long placeId : allPlaceIds) {
    placeComparator.comparePlaces(placeId, v2Map.get(placeId), v3Map.get(placeId), originalRequest);
}
// 4. 비교기는 차이가 있을 때만 로그를 남깁니다
if (!differences.isEmpty()) {
    log.info(result.toString());
}
```

동작만 보면 지금과 크게 다르지 않습니다.

샘플링을 하고 별도 스레드에서 두 로직을 호출한 뒤 숙소별로 비교합니다.

문제는 이 흐름을 만드는 데 들어간 코드의 양이었습니다.

어노테이션, Aspect, 비교기, 설정, 요청 컨텍스트, DTO, 서비스까지 PLP 쉐도잉에만 파일 13개에 1,500줄 정도가 들었고 그중 PLP 전용 비교기(PlaceComparator)가 887줄이었습니다.

그리고 ILP, PDP, RDP에도 각자 비슷한 구조가 따로 있었습니다.

나중에 V2↔V3 쉐도잉을 걷어낼 때 지운 코드만 57개 파일에 5,900줄 가까이 됐습니다.

결과도 차이가 있을 때만 로그로 남았기 때문에 일치한 요청이 몇 건인지는 알 수 없는 구조였습니다.

**지금: 라이브러리를 쓰는 PLP 쉐도잉**

지금 PLP 쉐도잉에서 쉐도잉을 호출하는 부분은 이것뿐입니다. 읽기 쉽게 spec() 메서드와 호출부를 합치고 일부 설정은 생략했습니다.

```
shadowRunner.run(ShadowRun.builder()
    .target("PLP")
    .comparator(comparator)
    .enabled(builderConfigProperties.isRateSearchShadowEnabledPlp() && !isPastCheckIn(param))
    .samplingRate(builderConfigProperties.getRateSearchShadowSamplingRatePlp())
    .request(request(httpRequest))
    .keyLabel("place")
    .primaryServed(asMap(mongo, plpProductParam, personalCount), servedMillis)
    .candidate(() -> asMap(rateSearchProductService.getProductsForPLP(plpProductParam, param), plpProductParam, personalCount))
    .build());
```

기존 로직이 이미 만든 결과는 그대로 넘기고 신규 로직은 샘플링을 통과했을 때만 별도 스레드에서 실행됩니다.

샘플링, 별도 스레드 실행, 키 매칭, 비교, 로그와 메트릭 보고, 양쪽 소요 시간 측정은 모두 라이브러리가 맡습니다.

그렇다고 애플리케이션 코드가 텅 비는 건 아닙니다.

asMap()은 인원 조건에 맞지 않는 객실을 양쪽에서 똑같이 걸러내고 isPastCheckIn()은 지난 날짜 요청을 비교에서 뺍니다. request()는 불일치가 났을 때 재현할 수 있도록 실제 API 요청의 URI와 body, 헤더를 그대로 담습니다.

이런 코드는 무엇을 같은 응답으로 볼지에 대한 판단이라 라이브러리가 대신 정할 수 없습니다.

오히려 반복되는 실행과 기록을 라이브러리가 가져가니 이런 판단이 코드에서 더 잘 보이게 됐다고 생각합니다. 주석까지 포함해도 PLP 쉐도잉 클래스는 200줄 남짓입니다.

**라이브러리 안에서는 무슨 일이 일어날까**

호출부가 이렇게 짧아진 건 예전 Aspect와 서비스가 하던 일을 라이브러리가 대신하기 때문입니다.

shadowRunner.run()을 호출하면 안에서 어떤 순서로 일이 일어나는지 따라가 보겠습니다.

![](https://images.gogumang.com/361d8e1cc1/20.gif)

**1. 요청 스레드에서는 쉐도잉 on/off와 샘플링 여부만 확인합니다.**

run()은 요청 스레드에서 호출됩니다. 그래서 여기서는 쉐도잉이 켜져 있는지와 샘플링에 걸렸는지만 확인합니다.

```
public void run(ShadowRun run) {
    if (!passesGate(run)) {
        return;
    }
    executor.execute(() -> execute(run));
}

// 요청 스레드에서 도는 값싼 검사
private boolean passesGate(ShadowRun run) {
    return run.enabled()
            && run.samplingRate() > 0
            && ThreadLocalRandom.current().nextDouble() < run.samplingRate();
}
```

통과하지 못하면 아무 일도 하지 않고 바로 돌아갑니다.

![](https://images.gogumang.com/361d8e1cc1/21.png)

통과하면 실제 작업을 실행기에 넘기고 역시 바로 돌아가기 때문에 사용자 응답은 쉐도잉을 기다리지 않습니다.

![](https://images.gogumang.com/361d8e1cc1/22.png)

Executor는 라이브러리가 만들지 않고 애플리케이션이 넘겨줍니다.

**2. 별도 스레드에서 두 결과를 확보하고 시간을 잽니다**

```
private void execute(ShadowRun run) {
    long startNanos = System.nanoTime();
    try {
        long primaryStart = System.nanoTime();
        Map<?, ?> primary = run.primary().get();
        long primaryMillis = run.primaryServedMillis() != null
                ? run.primaryServedMillis() : elapsedMillis(primaryStart);
        long candidateStart = System.nanoTime();
        Map<?, ?> candidate = run.candidate().get();
        long candidateMillis = run.candidateServedMillis() != null
                ? run.candidateServedMillis() : elapsedMillis(candidateStart);
        List<FieldDiff> diffs = compareMaps(run.keyLabel(), primary, candidate, comparator);
        ShadowResult result = diffs.isEmpty() ? ShadowResult.MATCH : ShadowResult.DIFF;
        reporter.executed(run.target());
        reporter.report(/* 대상, 판정, 요청, 소요 시간, diff를 담은 이벤트 */);
    } catch (Exception e) {
        reportError(run, startNanos, e); // ERROR로 보고
    }
}
```

앞의 PLP 코드에서 기존 결과는 primaryServed()로 넘겼습니다.

이미 사용자에게 내려준 값을 그대로 감싸 두는 것이라 여기서 get()을 해도 기존 로직을 다시 실행하지 않습니다.

소요 시간도 호출부가 재서 넘긴 값을 씁니다.

![](https://images.gogumang.com/361d8e1cc1/23.png)

신규 로직은 candidate()에 Supplier로 넘겼기 때문에 바로 이 시점에 처음 실행됩니다.

라이브러리는 실행 전후 시간을 재서 신규 로직의 소요 시간으로 기록합니다.

![](https://images.gogumang.com/361d8e1cc1/24.png)

대시보드의 “기존 vs 신규 소요 시간” 그래프가 이 두 값으로 그려집니다.

**3. 키로 짝을 맞춰 비교합니다**

![](https://images.gogumang.com/361d8e1cc1/25.png)

```
for (Object key : union(primary.keySet(), candidate.keySet())) {
    String prefix = keyLabel + "[" + key + "]";   // 예: place[10001]
    Object p = primary.get(key);
    Object c = candidate.get(key);
    if (p == null) { out.add(new FieldDiff(prefix, "(없음)", "present")); continue; }
    if (c == null) { out.add(new FieldDiff(prefix, "present", "(없음)")); continue; }
    for (FieldDiff d : comparator.compare(toJson(p), toJson(c))) {
        out.add(new FieldDiff(prefix + "." + d.path(), d.primaryValue(), d.candidateValue()));
    }
}
```

두 결과는 숙소 ID나 객실 ID를 키로 한 맵입니다. 라이브러리는 양쪽 키를 합쳐서 하나씩 짝을 맞추고 한쪽에만 있는 키는 그 자체로 차이로 기록합니다.

짝이 맞으면 두 객체를 JSON 트리로 바꿔 비교기에 넘깁니다.

기본 비교기(JsonTreeComparator)는 객체는 필드 단위로 배열은 인덱스 단위로 끝까지 내려가서 값이 다른 곳의 경로를 모읍니다.

여기에 keyLabel로 받은 이름과 키를 앞에 붙이면 대시보드에서 보던 place\[10001\].products.20022.stay.displayPrice.discountRatePerDay 같은 경로가 됩니다.

비교 규칙을 바꿔야 할 때는 비교기만 갈아 끼우면 됩니다.

PLP가 쓰는 RateSearchShadowComparator는 비교하기 전에 쿠폰 문서 ID나 실시간 카운트다운처럼 매번 달라질 수밖에 없는 필드와 사용자 화면에 나가지 않는 필드를 먼저 걷어냅니다.

정률 특가에서 1원 반올림 때문에 생기는 차이는 조건이 맞을 때만 흡수하고 몇 건을 흡수했는지 따로 셉니다.

무엇을 같은 응답으로 볼지는 이렇게 도메인마다 다르기 때문에 비교기는 애플리케이션 쪽에 두었습니다.

**4. 판정하고 보고합니다**

차이가 하나도 없으면 MATCH이고 하나라도 있으면 DIFF입니다.

신규 로직 호출이나 비교 도중 예외가 나면 ERROR로 보고합니다.

![](https://images.gogumang.com/361d8e1cc1/26.png)

보고는 reporter.executed()와 reporter.report() 두 번에 나눠서 합니다. 앞의 것은 “비교를 한 번 실행했다”는 기록이라 일치율의 분모가 되고 뒤의 것이 판정 결과입니다.

reporter는 사실 리포터 여러 개를 묶은 것입니다.

* LogShadowReporter: 이벤트를 SHADOW_EVENT라는 이름의 로거로 한 줄짜리 JSON 로그로 남깁니다. 이 로그가 Loki로 모여 대시보드의 원본 이벤트와 요청 목록 패널이 됩니다.
* MetricsShadowReporter: Micrometer로 실행 수, 판정별 건수, 양쪽 소요 시간, 필드별 불일치 수를 기록합니다. Prometheus가 이걸 수집해 대시보드의 일치율과 그래프가 됩니다.

![](https://images.gogumang.com/361d8e1cc1/27.png)

필드별 불일치 수를 기록할 때는 경로에서 대괄호 부분을 지워서 셉니다. room\[20022\].stay.displayPrice.discountRate와 room\[20001\].stay.displayPrice.discountRate가 모두 room.stay.displayPrice.discountRate 한 칸으로 묶이는 식입니다. 앞에서 본 __overflow__는 이렇게 묶은 필드 이름이 1,000종을 넘을 때 쓰는 칸입니다.

**5. 무슨 일이 있어도 사용자 응답은 건드리지 않습니다**

![](https://images.gogumang.com/361d8e1cc1/28.png)

라이브러리 곳곳에는 한 가지 원칙이 깔려 있습니다.

쉐도잉이 실패해도 사용자 응답에는 영향이 없어야 한다는 것입니다.

리포터를 묶은 CompositeShadowReporter는 리포터마다 예외를 따로 잡습니다. 로그 리포터가 실패해도 메트릭 리포터는 그대로 기록하고 실패한 건수는 shadowing_report_dropped_total로 따로 셉니다.

ERROR를 보고하다가 또 실패하면 그때는 조용히 포기합니다.

검증을 위해 붙인 코드가 장애를 만들면 본말이 뒤집히니까요.

참고로 이 모든 부품은 스프링 부트 스타터가 자동으로 등록합니다.

의존성을 추가하면 로그 리포터와 메트릭 리포터와 기본 비교기가 빈으로 올라오고 애플리케이션은 ShadowRunner를 주입받아 run()만 호출하면 됩니다.

**정리하면 이렇게 달라졌습니다**

* 적용 방식: 어노테이션과 AOP 대신 ShadowRunner를 한 번 호출합니다.
* 코드: API마다 따로 만들던 Aspect, 설정, DTO, 서비스가 없어지고 도메인 판단만 남았습니다.
* 결과: 차이가 있을 때만 남던 로그 대신 일치·불일치·ERROR가 모두 같은 형식의 로그와 메트릭으로 나갑니다.
* 재현: 불일치 이벤트에 실제 요청의 URI와 body, 헤더가 담깁니다.
* 성능: 기존 로직과 신규 로직의 소요 시간을 각각 잽니다.

새 API에 쉐도잉을 붙일 때 대시보드 쪽은 손댈 필요가 없어졌다는 게 가장 좋았습니다.

### 대시보드 하나로 달라진 것들

돌아보면 달라진 건 크게 네 가지입니다.

먼저 일치율을 집계할 수 있게 됐습니다. “대충 맞는 것 같다”가 아니라 몇 건 중 몇 건이 같았는지로 이야기합니다.

다음으로 로그를 보러 서버에 들어가지 않습니다.

대시보드에서 바로 Loki 로그로 이어지니 이상한 숫자를 보고 원문을 확인하기까지가 몇 초면 됩니다.

또 어떤 케이스에서 어떤 diff가 나는지 쉽게 파악됩니다.

필드별로 모아서 보고 요청 조건까지 같이 보이니까 재현하느라 헤매는 시간이 거의 사라졌습니다.

마지막으로 기존 로직과 신규 로직의 처리 시간을 같은 화면에서 비교합니다.

응답이 같은지와 느려지지 않았는지를 따로 확인할 필요가 없어졌습니다.

대단한 기술을 쓴 건 아닙니다.

메트릭을 모으고 화면을 하나 만든 것뿐인데 검증에 드는 사람 손이 눈에 띄게 줄었습니다.
