안녕하세요. 여기어때컴퍼니 광고플랫폼개발팀 지하입니다.

저희 팀은 설치형 ERD 솔루션으로 ERD를 설계하고 관리해 왔습니다. 쓰는 사람마다 프로그램을 설치해야 했고, 라이선스 비용도 들었습니다. 무엇보다 테이블을 하나하나 그리고 관계를 잇는 일을 전부 사람이 했습니다.

그래서 올해 초부터 AI로 ERD를 그릴 수 없을까 고민했습니다. 처음에는 AI에게 그려 달라고 하면 끝날 줄 알았습니다. 몇 번 시켜 보고 나서야, 매번 같아야 하는 일을, 시킬 때마다 답이 달라지는 비결정적인 AI에게 통째로 맡긴 게 문제라는 걸 알았습니다. 그래서 생각을 바꿨습니다. AI가 직접 그리지 않고, 도구를 써서 그리게 하기로요.

아래에는 그렇게 AI에게 줄 도구를 만들면서 부딪힌 문제와, AI가 도구를 헷갈리지 않고 쓰게 하려고 정한 설계 원칙을 정리했습니다.

### AI에게 그냥 그려 보라고 했더니

처음에는 아무 도구 없이 AI에게 그려 달라고 했습니다. Mermaid로 그리게도 해 보고, HTML로 그리게도 해 봤습니다.

생각처럼 되지 않았습니다. 배치가 원하는 방향으로 나오지 않았고, 제대로 그려지지 않을 때도 많았습니다. 팀의 규칙을 지키지 못하는 경우도 잦았습니다. 무엇보다 같은 걸 시켜도 시키는 사람마다 다른 결과가 나왔습니다. 틀린 곳을 매번 다시 바로잡다 보니 피로가 쌓였습니다.

AI의 답은 비결정적입니다. 같은 요청에도 매번 다르게 답할 수 있습니다. 그렇다면 매번 같아야 하는 일까지 AI에게 맡기지 말고, 매번 같은 결과를 내는 도구를 AI에게 쥐여 주면 되지 않을까 싶었습니다. 누가 시켜도 같은 ERD가 나오게 하는 것, 이것이 처음 세운 목표였습니다.

### 설계는 AI가, 그림은 도구가

처음부터 지금 모양은 아니었습니다. 가장 중요하게 생각한 건 “AI가 ERD를 대신 그려 주는 것”이었고, 처음에는 편집기 안에 채팅 창을 넣고 API 키로 AI를 붙이려고 했습니다. 그런데 준비하는 사이에 AI 서비스의 정책이 바뀌었습니다. 구독 계정을 다른 도구 안에서 쓰는 길이 막혀서, 편집기 안에서 AI를 쓰려면 구독과 별도로 쓰는 만큼 API 요금을 내야 했습니다. 한참 고민한 끝에 방향을 뒤집었습니다. AI를 도구 안에 넣는 대신, 도구를 AI에게 주기로 했습니다.

그러면서 역할도 나눴습니다. AI는 사용자와 대화하며 ERD를 설계합니다. 어떤 테이블이 필요하고 무엇을 어떻게 이을지 함께 고민합니다. 그렇게 정한 내용을 도구에 그려 달라고 요청하면, 실제로 그리는 일은 도구가 합니다. 대화는 이미 쓰고 있는 AI 클라이언트에서 하고, 제가 만든 ERD 도구는 MCP(Model Context Protocol)로 ERD를 그리는 기능을 AI에게 제공합니다.

### 같은 설계, 세 가지 그림

도구를 쓰면 그림이 얼마나 달라지는지 직접 비교해 봤습니다. AI가 설계한 가상 쇼핑몰 ERD 하나를 준비했습니다. 회원, 상품, 주문, 결제, 배송, 쿠폰, 리뷰 같은 테이블 20개와 관계 27개입니다. 이 설계는 그대로 두고, 그리는 방법만 바꿔 Mermaid와 HTML, 그리고 직접 만든 ERD 도구로 그렸습니다.

![](https://images.gogumang.com/01cc32e4d3/02.png)

*\[그림 1–1\] Mermaid로 그린 결과*

Mermaid는 테이블을 어디에 놓을지 스스로 정합니다. 테이블이 20개가 되자 그림이 가로로 길게 퍼졌고, 관계선은 멀리 돌아 다른 테이블 사이를 가로질렀습니다. 배치가 마음에 들지 않아도 손댈 방법이 없습니다. 표현에도 한계가 있었습니다. 타입에 공백을 쓸 수 없어 BIGINT UNSIGNED가 BIGINT_UNSIGNED로 바뀌었고, NULL 여부와 한글 이름은 설명 칸에 몰아 적어야 했습니다.

![](https://images.gogumang.com/01cc32e4d3/03.png)

*\[그림 1–2\] HTML로 그린 결과*

HTML은 표 모양을 원하는 대로 꾸밀 수 있습니다. 대신 테이블을 어디에 둘지, 선을 어떻게 이을지를 코드로 직접 정해야 합니다. 목록 순서대로 격자에 놓았더니 관계선이 서로 엇갈리고 카드 뒤로 지나가서, 어느 테이블과 이어지는지 따라가기 어려웠습니다. 읽을 만하게 만들려면 자리와 선을 손으로 다시 짜야 하고, 설계가 바뀔 때마다 그 일을 되풀이해야 합니다.

![](https://images.gogumang.com/01cc32e4d3/04.png)

*\[그림 1–3\] 직접 만든 ERD 도구로 그린 결과*

직접 만든 도구는 관계를 따라 이어진 테이블을 이웃 열에 놓습니다. 관계선은 직각으로 꺾여 테이블 사이의 빈 곳으로 지나가고, 테이블 위를 가로지르지 않습니다. 한 테이블 안에 한글 이름과 영문 이름, 타입, NULL 여부가 함께 보여서 설계를 검토하기도 쉽습니다. 무엇보다 같은 설계면 누가 그려도 같은 그림이 나옵니다.

![](https://images.gogumang.com/01cc32e4d3/05.png)

*\[그림 1–4\] 세 가지 그림 비교*

세 그림은 모두 같은 AI가 같은 설계로 그린 것입니다. 차이는 AI가 아니라, AI가 무엇으로 그렸느냐에서 났습니다.

### 사람이 손대지 않아도 읽히는 그림

그림 1–3처럼 되기까지 가장 오래 붙잡은 건 배치였습니다. 처음에는 관계선이 테이블을 가로지르고 서로 겹쳐서 알아보기 힘든 그림이 자주 나왔습니다. 화면이 의도하지 않은 모양으로 그려지는 것을 하나씩 바로잡는 데 시간이 많이 들었습니다.

그래서 자동 정렬을 만들었고, 간격 맞춤으로 테이블 사이에 관계선이 지나갈 자리를 확보했습니다. 그리고 관계선을 손으로 옮기는 기능은 일부러 뺐습니다. 관계선은 늘 도구가 고른 경로로 자동으로 놓입니다. 누가 그려도 같은 그림이 나와야 한다는 처음 목표를 지키려면 이 편이 맞다고 봤습니다.

사람에게 주는 기능도 같은 생각으로 정했습니다. 사실 처음에는 ERD를 관리하는 데 무엇이 필요한지 정확히 몰랐습니다. 그래서 팀에서 쓰던 도구를 많이 참고했습니다. 다만 그대로 옮기지는 않았습니다. AI가 도구로 그려 주면 사람이 직접 그릴 일은 점점 줄어들 것이라 봤고, 사람에게는 검토하고 다듬는 데 필요한 최소한의 관리 기능만 두었습니다.

![](https://images.gogumang.com/01cc32e4d3/06.png)

### AI가 헷갈리지 않는 도구

도구를 준다고 AI가 그 도구를 잘 쓰는 건 아니었습니다. MCP로 도구를 주면, 명시적으로 시키지 않는 한 어떤 도구를 쓸지는 AI가 정합니다. 사람은 메뉴를 보고 필요한 기능을 고르지만, AI는 도구 설명을 읽고 스스로 고릅니다. 답이 비결정적인 것처럼, 도구를 고르는 일도 비결정적입니다.

그래서 AI가 도구를 쓰도록 설명으로 설득하는 것도 필요했지만, 그보다 도구를 어떻게 설계하고 구성하느냐가 더 중요했습니다. 상황마다 맞는 도구가 선택되게 하는 데 가장 공을 많이 들였습니다.

#### 도구를 고르는 일부터 설계하기

AI에게 주는 MCP 도구는 13개입니다. 현황을 보는 도구, ERD를 고치는 도구, 정렬하는 도구, 내보내는 도구, 되돌리는 도구로 역할을 나눴고, 비슷한 일을 하는 도구는 하나로 합쳤습니다. 특히 ERD를 고치는 도구는 하나만 두었습니다. 고치는 길이 하나여야 AI가 헷갈리지 않습니다. 여러 군데를 고칠 때도 한 번에 받아서, 중간에 하나라도 막히면 아무것도 바꾸지 않습니다. 반쯤 고쳐진 채로 남는 일이 없게 하기 위해서입니다.

도구 설명에는 무엇을 하는지뿐 아니라 언제 쓰고 언제 쓰지 말아야 하는지도 적었습니다. 예를 들어 운영 DB에 반영할 SQL이 필요하면, AI가 SQL을 손으로 짜지 말고 바뀐 부분을 뽑아 주는 도구를 쓰도록 적어 두었습니다. 헷갈릴 만한 요청은 추측하지 않게 막았습니다. 같은 이름의 테이블이 둘이면 아무거나 고르지 않고 되묻고, 도구가 모르는 요청은 성공으로 넘기지 않고 거절합니다.

그리고 AI가 정하면 흔들리는 것은 아예 도구가 정하게 했습니다. 도구 없이 시키면 같은 요청에도 이름과 타입이 매번 달라졌습니다. 예를 들어 “주문 테이블에 쿠폰 할인 금액을 넣어 줘”라고 하면, 어떤 날은 discount_amount INT가, 어떤 날은 coupon_discount_price DECIMAL(10,2)가 나오고, 아예 새 테이블을 만들 때도 있습니다. 그래서 AI는 무엇을 만들지와 한글 이름만 정하고, 영문 이름과 타입, 테이블 자리는 도구가 정합니다. 도구에는 한글 낱말과 영문 이름을 짝지어 둔 낱말표(용어사전)와, “금액은 INTEGER”처럼 뜻이 같은 컬럼이 같은 타입을 쓰게 묶어 둔 규칙(도메인)이 들어 있습니다. 도구는 이것을 보고 영문 이름과 타입을 붙입니다. “판매금액”이라고만 주면 영문 이름 sales_amount와 INTEGER 타입이 붙는 식입니다.

![](https://images.gogumang.com/01cc32e4d3/07.png)

#### AI가 스스로 확인하고 바로잡게 하기

도구를 잘 골랐다고 끝이 아닙니다. AI가 자기가 한 일이 맞는지 확인할 수 있어야 합니다. 반영하기 전에 결과를 미리 보는 기능도 넣었지만, 측정해 보니 같은 설명을 읽고도 모델마다 습관이 달랐습니다. Opus는 편집할 때 거의 매번 미리보기를 썼고 Sonnet도 썼지만, Haiku는 한 번도 쓰지 않았습니다. 그래서 미리보기를 건너뛰는 모델도 확인할 수 있게, 고친 뒤 돌려주는 답에 바뀐 항목의 지금 모습과 바뀌기 전 값을 함께 담았습니다. 관계를 이으면서 저절로 생긴 컬럼처럼 딸려서 바뀐 것도 같이 보여 줍니다. 규칙마다 경고 문구를 붙이자는 안도 있었지만, 처리 결과를 그대로 돌려주고 AI가 직접 확인하게 하는 쪽으로 정했습니다.

![](https://images.gogumang.com/01cc32e4d3/08.png)

*\[그림 3\] 답에 결과를 담기 전과 후*

막혔을 때의 답도 같은 생각으로 만들었습니다. AI는 이 도구 말고도 셸 같은 범용 도구를 함께 쥐고 있어서, 전용 도구가 애매하게 답하면 범용 도구로 빠져나갑니다. 측정하던 중 한번은 상태를 묻는 도구가 열려 있는 ERD가 없다고만 답하자, AI가 다룰 파일이 없다고 판단하고 셸 명령으로 저장소를 뒤져 개발용 샘플 파일을 열고 고쳤습니다. 그 뒤로 도구의 답에는 다음 할 일까지 담았습니다. 아무것도 열려 있지 않아도 어떤 파일을 다루면 되는지 알려 주고, 막히면 어디서 왜 막혔는지와 어떻게 고치면 되는지를 함께 알려 줍니다. 잘못 지운 것도 새로 만들어 메우지 말고 되돌리기를 쓰라고 안내합니다. 새로 만들면 관계나 다이어그램 자리가 원래대로 돌아오지 않기 때문입니다.

### 정말 나아졌는지 재 봤습니다

도구를 고칠 때마다 AI가 정말 잘 쓰는지 확인하고 싶었습니다. 그래서 서브에이전트로 여러 모델에게 같은 일을 시키고 결과를 채점했습니다. 테이블 9개짜리 가상 쇼핑몰 ERD에 일부러 오류 3건을 심어 두고, 쿠폰 기능을 설계하는 요청 10개와 기존 ERD를 정비하는 요청 12개를 Claude Haiku, Sonnet, Opus에게 각각 맡겨 모두 여섯 번 실행해 봤습니다.

첫 측정 결과는 좋지 않았습니다. 작은 모델은 설명의 빈 곳을 추측으로 메우다 조용히 틀렸고, 그러고도 완료했다고 보고했습니다. 큰 모델은 이것저것 조회해 빈 곳을 메워 결국 맞췄지만 호출을 2\~3배 더 썼습니다. 원인을 모아 보니 11개였습니다. 테이블을 만들면 기본키가 저절로 생긴다는 설명이 빠져 여섯 번 모두 여기서 막혔고, 잘못된 요청도 성공으로 받아 주고 있었습니다. 미리 보거나 되돌리는 기능도 없었습니다. 이것들부터 시작해 세 번에 걸쳐 도구를 고쳤고, 고칠 때마다 다시 쟀습니다.

![](https://images.gogumang.com/01cc32e4d3/09.png)

*\[그림 4\] 개선 전과 후의 도구 호출 수와 실패한 호출 수*

여섯 번의 실행을 합치면 도구 호출은 272번에서 153번으로 44% 줄었고, 실패한 호출은 61번에서 3번이 되었습니다. Sonnet과 Opus는 실패가 한 번도 없었고, Haiku의 실패 3건도 요청을 마치는 데는 지장이 없었습니다. 여섯 번 모두 요청을 끝까지 반영했고, Haiku가 컬럼 이름 두 개를 규칙과 다르게 지은 것만 남았습니다.

모델마다 습관도 숫자에 드러났습니다. 가장 똑똑하다는 Opus가 오히려 호출을 가장 많이 썼습니다. 어떤 도구를 불렀는지 보니, 반영하기 전에 거의 매번 미리보기로 먼저 보고, 점검과 조회로 한 번 더 확인했습니다. 그림을 그려 확인하기도 했습니다. 꼼꼼하게 일하다 보니 호출이 늘어난 셈입니다. 반대로 Haiku는 미리보기 없이 바로 반영해 호출이 적었고, Sonnet은 가끔만 미리 보면서 비슷한 호출 수로 실패 없이 끝냈습니다.

가장 반가웠던 건 지운 테이블을 되살리는 요청이었습니다. 처음에는 테이블을 새로 만들어 버려 원래 테이블로 돌아오지 않았고, 그다음에는 되돌릴 편집 개수를 잘못 세고도 완료했다고 보고했습니다. 되돌리기를 최근 것부터가 아니라 고른 편집 하나만 되돌리게 바꾼 뒤로는, 세 모델 모두 원래 테이블을 그대로 되살렸습니다.

### 쓰고 나서 달라진 것

지금은 AI와 대화하면서 설계하고, 이 도구로 ERD를 그려 다른 사람들과 공유합니다. 저는 결제 관련 기능을 개발하면서 이 도구로 설계하고 있고, 다른 팀원도 서비스를 설계하는 데 쓰고 있습니다.

다이어그램을 그리는 시간은 거의 사라졌습니다. 예전에는 테이블이 많은 설계라면 리뷰하고 고치고 다시 그리는 시간까지 반나절쯤 걸렸습니다. 지금은 AI가 그리고 사람은 배치를 조금 손보고 검토하는 정도라 30분 안팎이면 됩니다.

### 마치며

올해 초에 고민을 시작할 때만 해도 AI에게 그려 달라고 하면 끝날 줄 알았습니다. 막상 해 보니 그리는 일은 도구에게 주고, AI에게는 무엇을 그릴지만 맡기는 쪽이 맞았습니다. 이름과 타입, 배치를 도구가 정하게 한 뒤로는 같은 설계면 누가 그려도 같은 그림이 나옵니다.

가장 공을 들인 곳은 AI에게 주는 도구였습니다. 사람은 메뉴를 보고 고르지만 AI는 설명을 읽고 스스로 고르다 보니, 비슷한 도구가 있으면 헷갈렸고 답이 애매하면 다른 길로 샜습니다. 그래서 비슷한 도구를 합치고, 모르는 요청은 거절하고, 답에는 결과와 다음 할 일을 담았습니다. 정말 나아졌는지는 감으로 알 수 없어서 여러 모델에게 같은 일을 시켜 가며 쟀고, 그러는 동안 실패한 호출은 61번에서 3번으로 줄었습니다.
